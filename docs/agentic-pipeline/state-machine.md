# State Machine Skill (Implemented as Rust Scripts)

> **Status: IMPLEMENTED** as a cross-platform `rust-script` binary: `.opencode/scripts/pipeline-state.rs` (the state machine, metrics reader, audit engine, and integrity verifier all in one). This document is the contract it implements. Agents reach it through the `pipeline-state` skill.

---

## Purpose

Agents are contextual. The same developer behaves differently mid-implementation than during a PR retry, and the Orchestrator orchestrating triage is in a different mode than one processing a blocker. Agents cannot reliably infer "where are we right now?" from raw issue text — and the pipeline needs one deterministic authority for state.

The state machine exists to answer, deterministically and for every agent that wakes up:

1. **Where are we?** — the current Phase of the pipeline.
2. **What happened to get here?** — the triggering event and prior phase.
3. **What is this phase trying to achieve?** — the phase's Goals (principle 3).
4. **What am I supposed to do in this phase?** — the agent's responsibilities + the playbook for this phase.
5. **What do I hand off when done?** — the next phase and its expected input.

---

## Design: A Minimal Skill + A Workhorse Script

Two pieces, working together. The split is deliberate and non-negotiable: **all state logic lives in the script; the skill is a thin loader.**

| Piece | Location | Role |
|-------|----------|------|
| **State Machine Skill** | `.opencode/skills/pipeline-state/SKILL.md` | **Minimal.** Does NOT encode the phase model, transition rules, or guard logic — those live only in the script + this doc. It carries how to *invoke* the script and *read* its output (action reference + an operational summary of the exit gates so an agent knows what a transition requires), and is loaded at agent start. |
| **State Machine Script** | `.opencode/scripts/pipeline-state.rs` | **Does all the work.** Reads real signals (issues, labels, branches, worktrees, templates, comments), computes the current phase, validates guards (prior-phase completeness), **executes the GitHub writes agents request**, appends the metric event, and prints the context block the agent consumes. |

The script is the source of truth for state logic; the skill is static glue. The agent combines both: the skill tells it *how to invoke and read* the script, and the script tells it *where it is right now*. **If the skill ever grows phase descriptions or transition rules, that is a bug** — the skill must never duplicate (and thereby drift from) the script.

## What the State Machine Reads and Controls

The script is the pipeline's eyes, gatekeeper, and **single writer**. It reads GitHub state, validates it, executes the writes agents request, and reports the phase context. Per [principles.md](principles.md#2-a-state-machine-gives-each-agent-its-phase-context):

| Signal | What it reads / validates |
|--------|---------------------------|
| **Issues** | Each issue's `state`, `labels`, `title`, and `body` — the raw signals it computes phase from and validates action requests against. |
| **Labels** | The label set (`backlog`, `planning`, `ready-for-dev`, `testing`, `audit`, `post-audit`, `cleanup`, `blocked`, `done`) matches the true phase. Mismatch = the script reports the discrepancy rather than trusting the label. |
| **Templates** | On `create-issue` and `edit-issue`, the drafted body is validated against the PO template sections (backlog type for create; every `edit-issue` body, since the issue body IS the PO backlog) — the only template conformance the script enforces. The plan scaffold is `templates/triage-plan-template.md`, assembled by the `planning → implementation` transition into the `## Triage Plan` feature-issue comment. Other bodies are drafted by agents to their templates; the script does not re-validate them. |
| **Comments** | Required comments exist per [github.md](github.md): `Status` (the only agent-facing prefix — blockers/escalations) on the feature issue (the single source of truth), plus the timeline comments (`## Triage Plan`, `## Developer <ST-id> — verification`, `## Fix Plan`, `## Development Summary`, `## Tests Runs`) and the machine-posted phase comments (`## Audit Verdict` from `audit-record`, `## Pipeline Improvement` from `record-improvement`, `## Final Status` from the `close-issue --to-phase done` close). The testing exit guard scans the **feature issue** for the tester's `## Tests Runs` verdict — the feature is the single source of truth. No auto `Status` comments are posted — transitions are recorded only in the event log. **The Product Owner never posts a comment directly** (`comment`/`post-comments` are gated to reject `product-owner`); **the issue BODY is the single PO Backlog — no `## PO Backlog` comment is derived or posted**. **Trusted-author comment filter (ST-4 / REQ-05):** on a PUBLIC repo, issue comments are an untrusted prompt-injection surface. Every comment-body read path (`get_issue_comments`, `latest_evidence_comment`, `count_verdict_comments_in_round`, and the audit/cleanup gate + orchestration-snapshot reads) requests `authorAssociation` and EXCLUDES any comment authored by a non-write-capable role (`NONE`/`CONTRIBUTOR`/`FIRST_TIME_CONTRIBUTOR`/`FIRST_TIMER`) — it can never become a `## Tests Runs` verdict, a context-brief input, or the `latest` evidence. Trusted roles = `OWNER`/`MEMBER`/`COLLABORATOR` PLUS the pipeline's own posting principal (`BOT`/`MANNEQUIN`) — excluding those would break verdict parsing and AC3. Each excluded comment emits a `guard.fired` metric event + a surfaced note (never silent). |
| **Prior-phase completeness** | The exit conditions of the previous phase (its Goals) are verifiably met. If not, the script blocks entry and reports what's missing. |

### Determinism rule

The state machine computes phase from **real signals only** — never from an agent's self-report. If an agent claims a phase is done but the exit conditions aren't met, the script blocks the transition. Phase transitions happen by the script updating labels, not by agent assertion.

### Single-writer rule

The state machine is the **only** thing that writes GitHub in the pipeline. Agents draft content and request actions; the script validates each request against the guards, executes it, and records the metric event. Agents read GitHub directly (viewing issues, comments, branches) but never write it. This is what makes the determinism rule enforceable: the same authority that decides state is the only one allowed to mutate state.

**One deliberate exception to single-writer** (configured in `opencode.json`, a non-state mutation): the **developer** pushes `git push origin HEAD:spec/<N>` (its work product lands on the spec integration branch; `main`/`master` and `HEAD:main` are denied). The orchestrator's former `git push origin main` doc-sync exception is **removed**: the post-audit gate now opens **ONE consolidated SPEC MAINT PR** through the machine (`maint-pr` — a single `maint/<N>` branch carrying the pipeline's own edits **and** the product docs; the machine FORCE-merges it as the privileged writer (`--admin`, which SKIPS the required `validate` check — the repo has auto-merge disabled, so `--auto` is not used), verifies the PR is `MERGED`, and records the `maint-pr` event only then), and the orchestrator's `git push origin main` is **denied** in its sandbox. Every *pipeline-state* write (issues, labels, comments, branches/worktrees, PRs, closes) is still the machine's alone.

### Ownership: asset vs authority

The state machine is both the pipeline's referee and a pipeline asset. Two distinct relationships, kept separate:

- **Runtime authority is non-negotiable.** During a run, the state machine is the single writer and phase authority, and it applies to *every* agent — including the Orchestrator. No agent bypasses it: no direct `gh`/`git` pipeline writes, no improvised transitions, no hand-editing state.
- **Maintenance is the Machinist's.** The state machine is a pipeline script, and the Machinist owns its code: it fixes, hardens, and extends `pipeline-state.rs`, `pipeline.json`, this doc, and the `pipeline-state` skill. It is the only agent that edits the state machine's logic. **The principles (`principles.md`) are above the Machinist** — it follows them and never edits them; a principle-level change is proposed to the human and applied only on approval.

Three gates make the maintenance ownership safe:

1. **The referee must stay honest.** Every state-machine edit must pass `test-scripts.ps1` before it counts — a change that breaks the guards or the metrics is itself a pipeline failure.
2. **Documented in the same pass.** The change is documented in the pipeline docs in the same pass as the code.
3. **Anti-tamper line.** The Machinist edits the state machine's *logic* (guards, transitions, metrics, validation) — **never the record**. The event log, audit verdicts, and error log are append-only and must never be rewritten, edited, or backdated. The record is the evidence the Auditor judges on; editing it destroys the audit.

The runtime authority is structural, not personal: the Machinist can improve *how* the machine decides, never *what* it has already recorded.

## The Action Request API

Agents do not call `gh`/`git` for pipeline operations. Instead, the agent runs the state machine script with an **action request**; the script validates, executes, records, and returns the result.

```text
pipeline-state.rs --action <action> --issue <N> [-Arguments...]
```

| Action | What the state machine does | Guards it validates |
|--------|------------------------------|---------------------|
| `context` | Prints the phase context block for the dispatched agent (add `--raw` for JSON). For `orchestrator` it ALSO prints the **orchestration snapshot** — linked plan #, spec-branch-ahead commit count, Evidence-on-plan, A2A file path, spec branch, open blockers — so the orchestrator sees what exists without re-discovering it | Issue exists |
| `help` | Enumerates the shipped action set with each action's **actor gate** — generated from `ACTION_SPECS`, the same table `actor_allowed` enforces, so the documented surface cannot drift from the enforced one. Needed no `--issue`; also reachable as a bare `--help` | Any actor; read-only |
| `create-issue` | Creates a **backlog** issue from a drafted body file (the only auto-created issue type — single-issue model). The drafted body is validated against the PO template sections, then posted as-is; **the issue BODY is the single PO Backlog** (no `## PO Backlog` comment is derived or posted — PO feedback #2688). Also adds the issue to the configured GitHub project with Status `Backlog` (best-effort). **ST-2 lock-on-create:** immediately after creation the machine locks the new issue's conversation (`lock_reason: off-topic`, reusing the issue number parsed from the create URL) so it is comment-safe at birth — a **best-effort** step (a lock failure is surfaced as a warning + `guard.fired` note, never fatal to creation; the `hardening-lock-open-issues` action reconciles). `temp:` harness issues are NOT locked. **The Product Owner's GitHub writes are this action plus `Status` comments (PO amendments, #2734)** — `post-comments` remains gated to reject `product-owner`. (The legacy `--issue-type impl-plan` path is retained for test/back-compat only; the pipeline never creates plan issues.) | Product Owner or Orchestrator; body conforms to PO template sections (backlog/bug); valid issue type |
| `edit-issue` | **Corrects a live issue's BODY.** Since the issue body is the single PO backlog, a split/scope change recorded only in a comment leaves the parent gating itself on clauses it no longer owns (#3210's human-approved split deadlocked exactly here: `create-issue` existed, `gh issue edit` is denied to every agent, and the parent had to be unblocked by a human). `--issue <N> --body-file <path>` REPLACES the body (explicit body file required — there is no implicit default). The replacement is validated against the **same PO template gate `create-issue` uses**; an invalid draft is refused naming its missing sections and nothing is written. **Lifecycle rules:** a `done` or `canceled` (CLOSED) issue is **refused** — a closed spec is revised by a NEW issue with `--revises`, never by editing this one; and in a live round (`implementation`/`testing`/`audit`) the edit is refused **unless the actor is `product-owner`** (triage must not silently rewrite the plan's contract mid-round; a scope change in a live round is the contract author's call). Idempotent: content identical after EOL/trailing-space normalization is a **NO-OP** that records nothing. A successful replace records ONE `issue.edited` event (`issue`, `body_hash` = FNV-1a 64 hex of the normalized body) — history is never rewritten; GitHub keeps the prior body in its own timeline. | Product Owner or Orchestrator; explicit `--body-file`; body conforms to PO template sections; refused when `done`/`canceled`; refused in `implementation`/`testing`/`audit` for every actor except `product-owner` |
| `triage-init` | Creates the A2A working file `.opencode/tmp/<issue>/triage.md` (ephemeral, gitignored) for triage deliberation, seeded from the triage template's per-agent `## <Agent>` sections plus a `## Discussion` section (idempotent — re-running is a no-op once the file exists). **The `intake → triage` transition auto-seeds this file** — the action is kept only as a manual fallback and is redundant with that side-effect | Orchestrator only |
| `tests-commit` | Persists the durable, reusable per-feature test suite `.opencode/tests/<feature>/` to `main` via the Contents API: `--issue <N> --feature <name>`. **The WHOLE feature directory is upserted** — every regular file at any depth (markdown, `scripts/*.ps1` levers, `fixtures/**`), not only top-level `*.md`: persisting markdown alone dropped QA executables/fixtures from `main` silently and forced a developer to commit them on the spec branch (#3197). **Text content is persisted LF-normalized** (CRLF→LF; a file is BINARY — and persisted byte-exact — only when a NUL byte appears in its first 8 KiB): the Contents-API write bypasses git's clean filter, so an un-normalized write of a Windows working tree (CRLF) put CRLF blobs on `main` while every git-committed blob on `spec/<N>` carries LF, and `sync-spec-branch` then reported a CONFLICT on whole files that are byte-identical modulo CR — an EOL artefact, never a content difference (#3145). Tests are per-feature-domain and accumulate across specs, so they are NOT spec-scoped — they ride main as the regression asset. **Silence is the defect:** a path that cannot be persisted (unreadable, or the Contents write fails) aborts the command with a `… were NOT persisted to main — nothing below is on main: <paths>` refusal naming every unpersisted path. Fails if the folder is missing or empty. The QA `**Feature tests:**` declaration accepts the literal `none` (case-insensitive, optional parentheses) as the sanctioned **no-suite, deliberately** form — a docs-only spec seeds nothing, so a `none` declaration persists nothing, fires no G-240 `guard.fired`, and prints `NO SUITES (declared none)`; a genuinely empty marker still warns | Orchestrator (auto side-effect of `triage → implementation`; shared with the Tester, who persists results after execution) |
| `update-plan` | Replaces one whole `##` section of the `## Triage Plan` timeline draft `.opencode/tmp/<issue>/triage-plan.md` (the plan the `planning → implementation` transition auto-posts on the feature issue): `--issue <feature> --section <key> --body-file <draft>` replaces that `##` section (idempotent — re-running overwrites only that section; all others are untouched). Sections: `software-architect`, `ui-ux`, `qa` (agent sections) and `summary`, `staffing`, `deployment`, `risks` (orchestrator sections). **The `planning → implementation` transition assembles the plan and fills all sections automatically** — the action is kept for edge/repair only | Orchestrator only; `--section` (one of `software-architect`/`ui-ux`/`qa`/`summary`/`staffing`/`deployment`/`risks`) + `--body-file` required |
| `transition` | Moves an issue to the next phase (updates the phase label, and mirrors the phase onto the GitHub project **Status** field — Backlog → Planning → Coding → E2E → Reviewing; `done` also maps to `Reviewing` (awaiting human review) and only `canceled` maps to `Done`; best-effort, never fatal). `--to-phase` is optional — inferred when the phase has a single legal exit (required for `implementation`/`testing`/`post-audit`). **`--to-phase done` is refused** — `done` is reached only through cleanup (`close-issue --to-phase done`, which labels it done and leaves it OPEN for manual human close). **Human-authorized pre-verdict rework (`--human-authorized`):** a binding human directive may add scope while an issue sits in `testing` with its round aborted before any tester verdict (so no `## Tests Runs` comment can exist yet, and the normal rework leg's evidence precondition cannot be met). Passing `--human-authorized` together with a non-empty `--reason` and a `--authorization-ref <url|comment-id>` on `transition --to-phase implementation` bypasses ONLY that leg's evidence exit guard and records an auditable `human.authorization` event; the flag is ignored on every other leg, and without a non-empty reason the guard still blocks. **Auto side-effects (idempotent) before the label change:** `backlog → planning` **seeds the A2A working file** `.opencode/tmp/<issue>/triage.md` (from the triage template's per-agent sections + `## Discussion`; on a `post-audit → planning` restart or an `implementation → planning` **rescope** the stale file is backed up and re-seeded fresh); entering `implementation` **assembles the plan into the `## Triage Plan` timeline draft** `.opencode/tmp/<issue>/triage-plan.md` (from the converged A2A file — no plan issue is created, single-issue model; on a rework re-entry the **Software Architect-authored** `fix-plan.md` is posted as a compact `## Fix Plan (round N)` instead, the fallback compaction was removed (H2): a rework round requires an authored, classified `fix-plan.md`; on a **rescope re-entry (`planning → implementation`) the FULL re-converged plan is re-posted** — the old plan comment is superseded, not "unchanged"), **persists the QA-seeded test suites** (`tests-commit`, feature names parsed from the QA Expert's `**Feature tests:**` line), and creates the spec branch `spec/<N>`; entering `testing` opens the spec PR (`spec/<N>` → `main`) — **or, on a POST-MERGE restart where `spec/<N>` was deleted by `delete_branch_on_merge` after the spec PR merged, the machine recreates `spec/<N>` from `origin/main`** (G-421 descent) **and opens NO PR, recording a `spec-branch.recreated` event: a NO-PR round, since a squash merge leaves the branch tree-equal to main so `gh pr create` could never succeed** (the Orchestrator must re-serve the root at the recreated tip before the tester runs; a branch that is absent with NO merged spec PR on record fails the transition CLOSED rather than inventing a branch); `testing → audit` merges the spec PR (blocked unless it is mergeable — **note: GitHub CI checks are DEACTIVATED until open-source** (`.github/workflows/validate.yml.disabled`, human decision 2026-08-25), so `statusCheckRollup` is empty and `pr_merge_guard` passes on merge state alone; re-enable checks by restoring the workflow filename). A failed side-effect aborts the transition cleanly — no half-state. **No auto `Status` comment is posted** — the feature issue is the single source of truth, agents comment explicitly; the transition is recorded only in the event log | Orchestrator only; source phase label removed, target label added; legal transition; prior-phase exit guard passes (planning's exit guard checks the plan deliverable: `.opencode/tmp/<issue>/triage.md` converged with all required sections + `## Convergence: agreed`; implementation's forward commit guard is bypassed for the backward rescope leg) |
| `close-issue` | Closes the issue as `done` (from the **cleanup** phase — teardown complete; the audit verdict was recorded at `audit-record --verdict success` (audit → post-audit) and the post-audit ran, then the Orchestrator transitioned `post-audit → cleanup`) or `canceled` (from any non-done phase). **The `done` close re-checks the verdict against the intended served commit and never compares against an empty string (#3197):** the intended commit resolves from the serving checkout, else the `spec/<N>` tip (remote, then local) — and when cleanup's `prune` already deleted that ref (its remote counterpart was gone after the squash merge), the guard falls back to the MERGED spec PR's recorded head oid (`gh pr list --head spec/<N> --state merged --json headRefOid`). The verdict's `Tested commit:` must equal that merged tip (a genuinely superseded head still fails, naming the merged head); **the stamp is parsed as its LEADING whitespace-delimited token (backticks trimmed) — only a bare 7–40-hex sha is accepted, so same-line context (`34567eb5 (spec/… tip; served tree …; env …)`) is ignored rather than compared whole; a malformed leading token is refused naming the recognised value with the hint *put the context on the next line***; when no serving record, no ref and no merged PR can vouch for it, the close is refused with a distinguishable `cannot resolve the intended served commit …` error. `--to-phase done` swaps the label `cleanup → done`, records the phase transition, posts the ONE `## Final Status` closing comment (the Orchestrator's outcome/doc-sync draft from `--body-file`, else the conventional `.opencode/tmp/<issue>/final-status.md`, with the machine's final metrics folded into a single `## Metrics` section — replacing the former separate metrics `## Status` comment; it also re-runs the ad-hoc-script scan and folds a machine-computed `## Ad-hoc Scripts` section listing any `.ps1`/`.js`/`.ts` improvised under `.opencode/tmp/<issue>/**`), and closes the issue; `--to-phase canceled` closes without a phase swap | Orchestrator only; `--to-phase done|canceled` required; `done` allowed only from cleanup (fail-closed on the same verification audit-record enforces) |
| `comment` | Posts a prefixed comment (`Status` only — blockers/escalations; `Evidence`/`Question`/free-form `Decision` are removed and refused with a pointer to the correct channel) from a draft the agent wrote using the comment templates in [templates/](templates/). **`--body-file` is REQUIRED (explicit-body-file rule):** the implicit `.opencode/tmp/<issue>/<prefix>.md` default is RETIRED — a draft left on disk from an earlier (often withdrawn) amendment was republished by a later `comment` that never named its body, so the caller must name the body it authored for THIS call and the machine can never pick up a foreign draft. The machine validates the body (Evidence must carry a verdict) then prefixes `## <Prefix>` and posts. **G-405:** the per-developer verification comment's documented header `## Developer <ST-id> — verification` is honoured — a body that already carries a `## Developer …` heading on ANY line, or a `dev-verify-<ST-id>.md` body file (title DERIVED from the filename), posts under that header instead of `## Status` (the prefix gate is UNCHANGED — arbitrary prose still gets `## Status`), and the machine never prepends a second header when the body already carries one (no double-head) | Prefix is `Status`; `--body-file` required; **`product-owner` is rejected** (the PO's only output is deterministic — see `create-issue`) |
| `create-worktree` | Creates a worktree **detached at the tip of the spec integration branch** `spec/<N>` (the developer works directly on the feature issue — sub-issues were removed; the branch is `spec/<feature>`, falling back to `main` when the issue is not a feature). Path defaults to `.worktrees/<N>`; `--force-clean` permits sweeping a NON-EMPTY leftover dir (H3; a dirty worktree is never swept). Detached worktrees allow many developers in parallel. **It runs `git fetch origin` (bounded by the command timeout) BEFORE resolving the ref, then reports the resolved COMMIT SHA** — the bare ref name once handed a developer a worktree at a stale remote-tracking `origin/spec/<N>` (created before the push), producing a rejected push and a lineage repair — in the success line and the `commit` event attribute (the reuse path records that worktree's own HEAD). **A relative `--worktree-path` is anchored at the REPO ROOT** (so the tree lands where the developer will `cd`, whatever directory the action was invoked from), and **success is reported only on VERIFIED reality** — the path must be a directory, carry a `.git` marker, and `git rev-parse --show-toplevel` from inside it must resolve to that same path. git exiting 0 is not evidence (a mocked/no-op git, a pruned registration, or a failed add can all exit 0 with nothing usable on disk). On failure the action prints a `BLOCKED:` line, records a `failed` event, and exits non-zero carrying git's own stderr — it never prints `WORKTREE CREATED` and never records a `success` it cannot prove (#3197). **Both worktree actions refuse to run at all while `FREDO_MOCK_GH=1` (the offline validation simulator) is set**, unless the harness opts in with `FREDO_MOCK_WORKTREE=1` — a real session with a stray mock flag must not be handed a simulated worktree | Developer only; issue labeled `ready-for-dev`/`testing` (single-developer pipeline; no assignee required). `testing` is accepted for the CI-fix path (G-164): a check that goes red on the open spec PR is fixed by a scoped commit on the spec branch while the feature is still in `testing`, so the developer must be able to obtain a worktree then |
| `remove-worktree` | Removes a worktree after the developer has pushed (path defaults to `.worktrees/<N>`; a relative path is anchored at the REPO ROOT, symmetric with `create-worktree`). **It judges THAT worktree's state, never the enclosing checkout's**: a path counts as a worktree root only when it carries a `.git` marker AND `git rev-parse --show-toplevel` from inside it resolves to that path — `git -C <plain dir>` answers for the ENCLOSING repo, which is how one agent's in-flight edits once blocked an unrelated teardown (#3197). The dirty refusal and the ignored-artifact pre-clean (`git -C <path> clean -fdX`) both run against the tree itself. A non-worktree path is swept only inside the pipeline-owned `.worktrees/` root (create-worktree debris); anywhere else it is refused (`not a worktree root`) so a mistyped path cannot delete an unrelated directory | Developer only; refuses dirty worktrees |
| `generate-work` | **Removed.** Sub-issues, the consolidated tester issue, and separate plan issues were dropped (PO decision): all work is tracked directly on the feature issue + the spec branch, and the tester posts its `## Tests Runs` verdict on the feature issue. Calling this action prints a removal note and never creates issues | any actor; no-op |
| `prune` | Branch + worktree hygiene: deletes local `spec/*`/`feat/*` branches whose remote counterpart is **gone** (deleted upstream), legacy merged `feat/*`, orphaned worktrees + unregistered `.worktrees/*` debris; with `--remote` also deletes `origin/spec/<N>` for every **CLOSED** spec (open-issue list read once; fail-safe — a failed/unparseable read skips the sweep) | Orchestrator only; idempotent; never `main`/`master`/other. Merged spec PRs auto-delete their head branch via the repo's `delete_branch_on_merge` |
| `sync-spec-branch` | **Spec branch ⇄ trunk sync** (#3198): merges `origin/main` into `spec/<N>` so an open spec PR stops being `CONFLICTING`. The MACHINE runs git because the resolution path was closed to every agent (the developer's sandbox denies `git merge main*`/`git merge master*` and plain `git merge origin/main` falls to the deny-all; the Orchestrator holds no `git checkout`/`git merge`; and permission grants are restart-inert, so a sandbox edit cannot unblock the run that needs it). Contract: `git fetch origin main` + `git fetch origin spec/<N>`, then a **MERGE** (`--no-ff`, published history preserved — never a rebase, never a force-push) performed in a **detached throwaway worktree** under `.worktrees/sync-<N>-<uuid>/` so the repo root's HEAD/index/working tree are never moved (the served tree keeps serving). **Nothing is auto-resolved:** on conflict the merge is aborted, the published `origin/spec/<N>` ref is asserted unchanged, and the command fails loudly naming the conflicted paths. On a clean merge it pushes `HEAD:spec/<N>`, checks the PR's `mergeable` (a still-`CONFLICTING` PR fails), records `spec-branch.synced` (`branch`/`main`/`tip`), and tells the caller to re-serve the root (G-032) before the tester runs. A branch already containing `origin/main` is a NO-OP. `--issue <N>` required | Orchestrator only; legal only in `implementation`/`testing` and the gate phases `post-audit`/`cleanup`; `spec/<N>` must exist on `origin`. Legal in the gate phases because the G-421 descent guard now also refuses at `post-audit → cleanup` (M5), and its remedy must be callable there |
| `align-root` | **Puts the repo root ON the spec tip** so the `implementation → testing` serving-currency guard (G-052) is satisfied without a hand-run preserve/align/restore dance. The Orchestrator has no `git checkout` grant, so every `→ testing` with the root on `main` used to cost a developer dispatch. Contract: `git fetch origin` (bounded), resolve `origin/spec/<N>`, then judge the **at-risk** *uncommitted* paths (dirty ∩ changed between HEAD and the target) **by content, not by dirt**: content **equal to the target** (EOL-insensitive) is provably redundant — the planning-time `tests-commit` reconcile was committed to `origin/main` and the spec branch was cut from it — so it is allowed, restored losslessly from the target, and reported as `discarded-redundant` (never silently); content equal to HEAD is reported as restored-from-HEAD; **content differing from BOTH the target and HEAD is real in-flight work and REFUSES, naming every such path** (an untracked path has no copy at either rev and always counts as real). Otherwise `git checkout -B spec/<N> origin/spec/<N>` and report HEAD, the preserved dirty set, the discarded-redundant set, and whether HEAD matches the tip. **Never `-f`, never drops a stash, never commits.** Records `root.aligned` (`branch`/`head`/`target`/`preserved`/`discarded_redundant`/`restored_from_head`/`tree_matches_tip`/`root_lease`). **M1 ROOT LEASE (the sequential handoff):** the repo root is ONE resource, so the successful align also **ACQUIRES the root lease** — one persisted record `.opencode/state/root-lease.json` naming the spec that holds the checkout. The remote head is removed by `delete_branch_on_merge` and the local ref is swept best-effort, so the merge step never moves the serving checkout. **The merge command's exit status is not the verdict — the PR's state is:** the machine verifies `gh pr view <n> --json state,mergeStateStatus` on a bounded interval/timeout, records success when the PR is `MERGED` (with `merge_cmd_error: true` when the command nonetheless complained), and errors only when it is not (`MERGED`/`CLOSED`/timeout). **Checkout cleanliness (#3192, base-relative #3145):** `git checkout -B maint/<N> origin/main` rewrites every path that differs between HEAD and `origin/main`, so the refusal set is the **full** dirty × changed intersection (not just the post-audit paths — a build artefact such as `apps/tauri/src-tauri/gen/schemas/*` or `apps/tauri/src-tauri/Cargo.toml` is in that set). A dirty path is judged by **content loss against the PR's BASE `origin/main`**, not by dirt against HEAD: the serving checkout stays on `spec/<N>`, which can predate a human commit on `main`, so a path can be dirty against HEAD yet byte-equal (EOL-insensitively) to the base the checkout writes. A path is exempt when **neither its worktree nor its index would lose work** — each equals `origin/main` (what the checkout writes) or `HEAD` (already committed, recoverable). **Exempt paths are then RECONCILED before the switch:** `git checkout -B maint/<N> origin/main` refuses a ` M` path (index at HEAD, worktree at the base) *even when its working tree already equals the target*, so each exempt path is restored to the revision its content already equals (`origin/main` for a base-equal path, `HEAD` for an EOL-only one) — ONE reconcile path, its source picked by the **worktree** content. The equality assertion runs **before** the write, judges **both** the worktree and the index and names **both** revisions (`HEAD`, `origin/main`): a path is **never** reconciled to a revision its content does not equal, and a failed reconcile **fails loudly** — naming the path, the expected revision and the actual diff — instead of proceeding into a switch it cannot satisfy. The reconcile is **content-neutral** (the on-disk bytes are unchanged — the path already equals its source). It ranges over **git's refusal set, NOT the PR's path list** — the paths that block a switch are not limited to the paths the PR commits (`.gitattributes` is outside it and still blocks). For `.gitattributes`, read by git from the **working tree**, a wrong reconcile to HEAD is **invisibly damaging**: the policy is committed on `main` (no data loss, no error), but the checkout's line-ending policy is silently disabled — no diff appears in any artefact a reader inspects. **Both exemptions are the ONE content predicate `align-root` uses to call a dirty path provably redundant** (its `worktree_matches_rev` / `index_matches_rev` core), applied to `origin/main` and to `HEAD`. Only a path whose content differs from **both** refuses — naming the path and telling the addressed role to **REPORT it to the human** (no agent holds a repo-root move grant; the machine never forces a checkout and never discards work). The `maint-pr` event is recorded **only once the PR is actually `MERGED`** (`merged: true` + `branch`/`pr`/`url` attrs); a PR that is not `MERGED` (closed unmerged) or a timeout is an **error** — the gate must fail so `done` stays unreachable. **Reconciliation / idempotency:** a merge that LANDED but was never recorded would otherwise deadlock the gate forever (`done` unreachable), so when nothing is left to commit the machine asks GitHub whether a `maint/<N>` PR is already `MERGED` and, if so, records the event (`merged: true`, `reconciled: true`, with the PR number/url) and prints the merged-PR line instead of concluding. A NO-OP is printed only when there is genuinely nothing to commit **and** no merged maint PR exists — and it records **no event** (a NO-OP is not an outcome; recording one would claim a maintenance sync that never happened). An empty change set is a NO-OP (never fatal — no PR, no merged event). **Flow:**
1. Agent reads GitHub directly (context, signals, prior comments).
2. Agent drafts content to a temp file (issue body, comment body).
3. Agent runs `pipeline-state.rs --action ...` with the draft path + arguments.
4. The script validates the request against the guards → executes the write → appends the metric event → returns the result (e.g., new issue number, comment URL).
5. If a guard fails, the script returns `BLOCKED: <reason>` and the agent does not get the write.

**Why this matters:** because every GitHub write goes through the state machine, there is no way for an agent to mutate state without passing the guards — the anti-Goodhart structural guarantee from the Metrics section is enforced at the write layer, not just reported.

### Transition side-effects (the machine owns the mechanics)

The mechanical orchestration steps are now **transition internals** — deterministic side-effects the state machine executes automatically, so no agent runs them by hand:

- **`backlog → planning` — A2A seed.** The machine auto-seeds the A2A working file `.opencode/tmp/<issue>/triage.md` (idempotent). The Orchestrator does NOT run `triage-init` manually.
- **`planning → implementation` — plan assembly + test persistence + spec branch.** The machine (a) assembles the plan into the `## Triage Plan` timeline-comment draft `.opencode/tmp/<issue>/triage-plan.md` (from `docs/agentic-pipeline/templates/triage-plan-template.md`, filling every section — `software-architect`, `ui-ux`, `qa`, `summary`, `staffing`, `deployment`, `risks` — from the converged A2A file) and posts it ON the feature issue; (b) persists the QA-seeded test suites to `main` via `tests-commit` (feature names parsed from the QA Expert's `**Feature tests:** <name1, name2>` line in the A2A file — matched leniently, so a leading blockquote `>` / whitespace before the marker does not silently drop the declaration, **but the tokens AFTER the marker must themselves be bare comma-separated lowercase-kebab names**: a marker embedded in a comma-rich sentence parses to ZERO names, and the transition now surfaces a `WARNING:` note + a `guard.fired` (G-240) instead of skipping silently — **except** the sanctioned no-suite form: the literal `none` (case-insensitive, optional parentheses) means the spec deliberately seeds nothing, so nothing is persisted, no guard fires, and the transition notes `NO SUITES (declared none)`; an empty marker still warns) — **only on the FIRST entry into implementation**; a rework (`testing → implementation`) or rescope (`implementation → planning → implementation`) re-entry skips suite persistence, because the root checkout may sit on a spec branch whose `.opencode/tests/**` copies predate the tester's later suite extensions and re-persisting from that stale tree would revert main's guidance (the G-038 hazard); (c) creates the spec branch `spec/<N>`. **Single-issue model: no sub-issues, no tester issue, and no separate plan issue are created** — all work is tracked directly on the feature issue + the spec branch, and the tester posts its `## Tests Runs` verdict on the feature issue.
- **`→ testing` — spec PR (or a NO-PR round after a merge).** **G-421 descent RE-CHECK (before the PR step):** when `spec/<N>` exists on `origin` but does NOT descend from `origin/main` (`git merge-base --is-ancestor origin/main origin/spec/<N>` fails), the transition is REFUSED with a pointer to `sync-spec-branch` — the trunk advanced under a live spec, so the PR is (or will be) `CONFLICTING` and entering a test round would burn it (#3198: `spec/3198` was cut from `main@696f5a6`; #3197 then rewrote the same OpenCode doc passages, leaving PR #3205 `mergeable: CONFLICTING`). The check runs on every `→ testing` leg (a missing branch is left to the post-merge recreate path below). The machine opens the spec PR (`spec/<N>` → `main`) if one is not already open — but only when the branch carries commits beyond `main` (a branch with none cannot back a PR: `gh pr create` fails `No commits between main and spec/<N>`). **POST-MERGE RESTART:** when the feature re-enters `testing` (an audit restart — `testing` is one of the four phases the Auditor may restart to) and `spec/<N>` is absent because the spec PR was SQUASH-merged and `delete_branch_on_merge` deleted the head, there is nothing to open a PR from and nothing left to merge (a squash merge leaves the branch tree-equal to `main`). The machine then **recreates `spec/<N>` from `origin/main`** (G-421 descent — never from the old round tip; `update-ref`/`git branch`, never `git checkout -b`, so a dirty tree from planner-seeded suites is untouched, G-038) and opens **NO PR**, recording a `spec-branch.recreated` event (`pr: none`, `reason: already-merged`) so the Orchestrator and the Auditor can see the round is PR-less. The Orchestrator must re-serve the root at the recreated tip (G-032) before the tester runs — the tree is the same (squash merge), but the commit SHA is new, so `servedCommit` in the env evidence necessarily changes and a stale serving record must be refreshed. **If `spec/<N>` is absent and NO merged spec PR records the work** (a genuinely lost branch), the transition fails CLOSED with an actionable message — it never invents a branch whose PR would show nothing (main-based) or replay stale work.
- **`post-audit → cleanup` — G-421 descent at the GATE (M5).** The SAME "a branch behind `origin/main` is refused" rule that guards `implementation → testing` also applies to the success exit: when `spec/<N>` exists on `origin` but does not descend from `origin/main` (`git merge-base --is-ancestor origin/main origin/spec/<N>` fails), the transition to `cleanup` is REFUSED with the same pointer to `sync-spec-branch`. Rationale: a PASS round never re-enters `testing`, so the leg the sync obligation was deferred to ("before the next `implementation → testing`") never came, and a branch that fell behind mid-round reached the gate unchecked (#3145: round 3 passed, main advanced, the stale branch surfaced inside the gate). **A PASS is the COMMON case, so the gate must not be the unchecked leg.** The remedy action (`sync-spec-branch`) is now callable in the gate phases — a refusal must name a remedy the addressed actor can actually run. (A missing `spec/<N>` remains a no-op here — the post-merge recreate path owns that state, as on `→ testing`.)
- **`post-audit → cleanup` — ad-hoc-script surfacing (#3077).** Entering `cleanup` scans the issue's scratch tree `.opencode/tmp/<issue>/**` for `*.ps1` / `*.js` / `*.ts` (recursive, `node_modules` skipped, repo-relative forward-slashed sorted paths) and **prints + records** the inventory: an `AD-HOC SCRIPTS (N): …` line (or `AD-HOC SCRIPTS: none …`) and an additive `ad-hoc-scripts` metric event carrying `count` + the comma-joined `scripts` paths. The `close-issue --to-phase done` close re-runs the same scan (so the recorded list reflects the final scratch tree) and folds a machine-computed `## Ad-hoc Scripts` section into the ONE `## Final Status` comment. **Best-effort and additive** — a missing/unreadable directory yields `none`, a failed event append is swallowed, and neither ever blocks the transition or the close. It exists so scripts an agent improvised during the run are surfaced for promotion: the Orchestrator routes recurring ones to the **Toolsmith** (the tooling library) instead of losing them with the scratch dir.

The planning exit guard is now **only** the plan deliverable — `.opencode/tmp/<issue>/triage.md` must be converged (all required sections + `## Convergence: agreed`); no GitHub `Decision` convergence comment is posted. If an agent looks for a GitHub comment and finds none, it reads the `.md` files under `.opencode/tmp/<issue>/`. The manual `triage-init`, `tests-commit`, and `update-plan` actions are kept for edge/repair only; the transition owns the happy path. The issue BODY is the single PO Backlog (the PO never writes a comment directly).

**Timeline comments (posted by every transition + `audit-record`):** the feature issue is the single source of truth, and its timeline is built from five titled comments — `## Triage Plan`, `## Developer <ST-id> — verification` (per developer, at implementation — before `## Tests Runs`; posted by the `comment` action, or flushed from a `dev-verify-<ST-id>.md` draft — the title is DERIVED from the filename; the two channels are idempotent — the flush recognizes an existing verification by the header on ANY line, INCLUDING the nested header of an older `## Status`-headed comment, and consumes the stale draft instead of duplicating it, and never prepends a header a body already carries — no double-head), `## Fix Plan (round N)` (rework re-entries), `## Development Summary`, `## Tests Runs` — plus the **machine-posted phase comments**: the Auditor's `## Audit Verdict` (from `audit-record`; structured body via `--body-file`/`.opencode/tmp/<issue>/audit-verdict.md`, else a sane default; the machine owns the header, the `Verdict:` line, and the `*Authored by Auditor*` footer — the Auditor's ONE message at its turn), the Curator's `## Pipeline Improvement` (from `record-improvement`; **ONE per curation pass, never one per guardrail**), and the Orchestrator's `## Final Status` (from the `close-issue --to-phase done` close — the outcome/doc-sync draft + the machine's final metrics, folding the former separate metrics `## Status` comment). **The issue BODY is the single PO Backlog** — no `## PO Backlog` comment is posted (it duplicated the body; PO feedback #2688). Agents draft each as `.opencode/tmp/<issue>/<file>.md` (`triage-plan.md`, `fix-plan.md`, `dev-verify-<ST-id>.md`, `dev-summary.md`, `tests-runs.md`, `audit-verdict.md`, `pipeline-improvement.md`, `final-status.md`) using the templates in [templates/](templates/); the state machine reads each pending draft and posts it (consuming the file) as part of the transition / `audit-record` / `record-improvement` / `close-issue`. A `## Tests Runs` draft is **refused unless it carries a literal `Verdict:` line** (a malformed "PASS 7/7" header is kept for the tester to fix), **and refused if any image reference lacks `https://`** — a bare screenshot filename or local `.opencode/tmp/` path is unviewable/unopenable on GitHub (observed #2756 round 2), so the machine keeps the draft until every image is an `upload-evidence` raw URL. The `## Tests Runs` comment carries the tester's verdict and is the ONLY comment the verification gate reads for evidence. A `post-comments` action flushes pending drafts manually.

**Retry-round plan compaction:** the full `## Triage Plan` is posted once at the first `planning → implementation`. On a rework re-entry into implementation (`testing → implementation`, i.e. a prior `phase.started` for `implementation` exists), the machine does NOT re-post the full plan. The fix scope is designed by the **Software Architect**: the Orchestrator dispatches the architect (with the tester's FAIL verdict) BEFORE the transition; the architect writes `.opencode/tmp/<issue>/fix-plan.md` (`Root cause class: defect|technique|environment|scope` as the first content line, then `## Failed ACs`, `## Root Cause (file:line)`, `## Fix Scope`, ending `*Authored by Software Architect*`), and the machine posts it as the compact, round-stamped `## Fix Plan (round N)` — consuming both drafts so nothing double-posts. **The class line is mandatory**: the machine records it as a `rework.rootcause` event attribute (the per-round WHY the Curator trends — most rounds burn in this loop, not at audit) and refuses to post an unclassified draft. **One channel (H2):** the fallback compaction was removed — a rework re-entry without an authored `fix-plan.md` posts nothing and warns; the Architect must author the classified draft. The orchestrator never authors fix scope itself. **A RESCOPE re-entry (`planning → implementation` after an `implementation → planning` rescope) re-posts the FULL re-converged plan** — the scope changed, so the old plan comment is superseded, not "unchanged" (the Fix Plan preamble would be false). The compaction decision keys on the SOURCE phase of the transition: `testing` compacts, `planning` (rescope) re-posts full, and a manual `post-comments` flush keeps the prior-implementation heuristic. A stray `fix-plan.md` on a FIRST entry is never posted (kept on disk with a warning). The `audit-record` restart flushes pending drafts **before** appending its destination `phase.started` (mirroring the `transition` handler), so the `## Fix Plan (round N)` header always equals the retry round — an earlier ordering flushed after the append and stamped an off-by-one round (header `round 3` while the retry context read `round 2`). **Round authority (B1):** `round_authority()` derives the ending round (Tests Runs) and the entering round (Fix Plan + Development Summary) from ONE event-log read, so the three artifacts can never disagree (G-427); Fix Plan and Development Summary share the entering round, Tests Runs uses the ending round. **Runtime bounds (F1):** every `gh`/`git` call is bounded (default 120 s, `FREDO_CMD_TIMEOUT_SECS` override) and fails with a typed error on timeout. **Verdict freshness (B5):** a `Tested commit: <sha>` line in `## Tests Runs` must match the intended served commit — a stale-head verdict is rejected.

**Rounds advance on every rework:** `retry_state`'s round is the count of `phase.started` entries for `testing`, advanced EARLY while a rework is in flight — an implementation re-entry from `testing` (tester-FAIL rework) or `audit` (restart) also counts, so an agent dispatched ONTO the rework (before the next testing entry lands) sees the correct round and the RETRY marker, never "round 1"; the retry *reason* still comes from failed `audit.verdict` events. Round-stamped comments: `## Development Summary (round N)`, `## Tests Runs (round N)`, `## Fix Plan (round N)`.

**A refused verdict draft fails the testing exit CLOSED (#3152).** Any leg leaving `testing` flushes the pending `tests-runs.md` BEFORE evaluating the exit guard. A draft that the content gate refuses (G-013 no `Verdict:` line, G-104 unviewable evidence) is KEPT — and after that refusal the transition is **blocked**, not completed, while the ENDING round has no verdict-carrying comment. Rationale: completing it would advance the round stamp (a rework re-entry counts) with the round's verdict unposted; the corrected draft would then flush under the ADVANCED round, collide with the next round's legitimate verdict under G-020, and deadlock the leg with no reconcile path. The block records a `guard.fired` (`guardKey: verdict_draft_refused_counter_advance`, `failureClass: round_advanced_without_verdict`). Remedy: fix the draft so it passes the gate (or hold it aside), then re-run the transition. A leg that already has its round verdict posted is unaffected — the guard only fires on an unposted round. The human-authorized pre-verdict rework is EXEMPT (a binding directive that already overrides the evidence guard must not be stranded by a leftover draft).

**Project Status sync (labels + Status):** alongside the phase labels, every transition mirrors the new phase onto the configured GitHub project's **Status** single-select field (`Backlog → Planning → Coding → E2E → Reviewing`; `create-issue` adds the issue to the project; `close-issue --to-phase done` sets `Reviewing` — the spec is finished but awaiting human review — while `close-issue --to-phase canceled` sets `Done`). The issue is added on first sync; on `done` it stays OPEN (manual human close) with Status = `Reviewing`; only a `canceled` issue reaches the `Done` column. **Every `gh api graphql` variable is passed with `-f` (raw string), never `-F`** (#3071): `gh` coerces an all-digit `-F` value to an Int, and GitHub rejects an Int against a GraphQL `String!` variable (`Could not coerce value 98236657 to String`). The `canceled` option id (`98236657`) is all digits, so `-F o=…` failed the whole canceled leg while the alphanumeric phase option ids (`f75ad846`, `df73e18b`, …) passed as strings. Best-effort and fail-safe — a sync failure logs `[project-status]` **and is recorded as a `state_machine.failure` event** (attributes `site: sync-project-status`, `phase`, `reason`) so a stalled Status transition is visible in the log/metrics instead of vanishing silently, but it is still never fatal to the create/transition/close it runs alongside.

## The Phase Model

Seven pipeline phases, matching [pipeline.md](pipeline.md). Each phase declares its Goals (principle 3), entry conditions, owner, and transitions.

**Metric anchors (fixed by policy):** commitment point = the Backlog→Planning handoff (lead-time clock starts); delivery point = Cleanup→Done (cycle-time clock ends). Cycle time = Implementation entry → Done; lead time = commitment → Done. Backlog/Planning count toward lead time only. See [Metrics](#metrics-the-pipelines-memory).

| Phase | Entry condition | Owner | Exits to |
|-------|-----------------|-------|----------|
| `blocked` | Any issue labeled `blocked` (a condition on any active phase, not a step in the flow) | Orchestrator (within SLA) | the phase it was blocked from (unblocked) |

**Agreement gate (planning):** leaving planning requires the plan deliverable to be converged — `.opencode/tmp/<issue>/triage.md` must carry all required sections and the `## Convergence: agreed` marker appended by the Orchestrator once no unresolved items remain in the `## Discussion` section. **No GitHub `Decision` convergence comment is posted** — the plan file is the artifact; if an agent looks for a GitHub comment and finds none, it reads the `.md` files under `.opencode/tmp/<issue>/`. The plan does not need to pre-exist as a GitHub artifact: the `planning → implementation` transition assembles it into the `## Triage Plan` comment on the feature issue (from the converged A2A file), persists the test suites, and creates the spec branch. No sub-issues, tester issue, or separate plan issue are generated — the plan's `- [ ]` checklist is the work list.

## The Context Block (Script Output)

`pipeline-state.rs` prints a block the agent reads at start. Contract:

```text
=== PIPELINE STATE ===
Phase:            <backlog|planning|implementation|testing|audit|post-audit|cleanup|done>
Feature:          #<backlog issue number>
Phase owner:      <agent name>
Triggering event: <e.g. "Implementation Plan posted", "PR #42 merged">
Previous phase:   <phase>
Goals:            <the phase's definition-of-done — measurable outcomes>
Playbook:         <how-to for this phase — the steps the agent follows, pointer to docs>
Responsibilities: <the agent's actions in this phase — pointer to docs section>
Handoff:          <next phase + what must exist for the transition>
Validation:       <what the script checked and passed, or what is blocking entry>
Doc references:   <pipeline.md#..., github.md#..., staffing.md#...>
--- (orchestrator only: orchestration snapshot) ---
Impl plan:          <plan # or "none">
Spec branch ahead:  <count of commits on spec/<N> not on main>
Evidence on plan:   <true/false — tester posted ## Tests Runs>
A2A file:           <.opencode/tmp/<issue>/triage.md or "none">
Spec branch:        <spec/<N> or "absent">
Open blocked:       <count of open blocked issues>
====================
```

### Inputs the script reads
- Issue `state`, `labels`, `title`, `body`.
- Comments on the issue, checked against the prefix rules ([github.md](github.md)).
- The dispatched agent's role (from the dispatch prompt).

### Output contract rules
- **Deterministic:** same input signals → same phase + validation result. No LLM judgment in the script.
- **Role-scoped:** the Playbook in the context block is filtered to the dispatched agent's role — a Developer waking up sees the Developer playbook, not the orchestrator's. The other fields (goals, responsibilities, doc references) are the same generic text for every agent.
- **Referenced, not duplicated:** the context block points at doc sections rather than restating their content, so there is exactly one authoritative definition.

## How Agents Consume It

1. Agent wakes (dispatched by its parent or the human).
2. Agent loads the `pipeline-state` skill (minimal loader: how to invoke the script, how to read its output, how to request a GitHub action).
3. Agent runs `pipeline-state.rs` with its role → gets the context block.
4. Agent reads its Goals (what "done" means) + Playbook (how to do it), performs its work.
5. **To write GitHub** — the agent drafts content to a temp file and runs `pipeline-state.rs --action <action> --issue <N>`. The script validates the request against the guards, executes it, records the metric event, and returns the result. **The agent never calls `gh`/`git` to write.** It reads GitHub directly for context.
6. Agent completes its handoff artifact (the state script's "must exist for transition" signal) and returns.

## Metrics: The Pipeline's Memory

The state machine is called by **every agent on every call** — and each call is a telemetry event. Because the state machine is the choke point, it is also the pipeline's passive metrics collector: agents never think about metrics; the call itself is the measurement. This is principle 2 point 3 ("It is the pipeline's memory") made concrete, and it is what the Auditor audits against (principle 6).

### Storage: per-issue JSONL event log

- **Format:** JSONL (UTF-8, one JSON object per line, `\n` terminator).
- **Location:** `.opencode/state/issues/<issueNumber>.jsonl` — **one file per issue**, appended by the state machine.
- **Why per-issue files:** single-writer by construction (only the agent handling that issue calls the state machine for it → no locking, no corruption); trivial retention (delete/gzip on issue close); cross-issue queries scan many small files, which is fast at this scale.
- **Raw events are the system of record.** All metrics are **derived from the log on demand** — never stored incrementally. This is event sourcing: the log gives complete rebuild, temporal query, and replay; aggregates are caches, not truth. (Avoids the high-cardinality trap of pre-aggregating `actor × issue × phase` totals at write time.)
- **SQLite is the escape hatch, not the starting point.** If query complexity/frequency grows, import the log into SQLite as a derived read model; the JSONL stays the source of truth.

### Anti-metrics — what we deliberately do NOT track

From the Goodhart research. These are signals, never targets, and never agent rewards:

- **First-pass rate / cycle time as a target** — optimizing them invites trivial tests and state-gaming. They are diagnostics.
- **Raw token minimization** — token spend explains ~80% of agent success; cutting it cuts solves. Track `costPerDoneFeature`, never tokens alone.
- **Velocity / raw issue counts** — no sprints; counting raw issues invites splitting to inflate throughput. Count verified-Done only, weight by AC scope.
- **Metrics as agent performance evaluation** — explicitly frame all metrics as pipeline-health/self-improvement inputs, never as agent performance reviews (malicious-compliance risk).

### Structural integrity guardrails (the anti-Goodhart layer)

- No skipped/illegal phase transitions (policy-enforced).
- Timestamps monotonic, RFC 3339 UTC, commitment point locked by policy.
- Append-only event log — history can never be rewritten or backdated. Appenders write each record + newline in a **single `write_all`** (atomic at the syscall level), so concurrent state-machine invocations cannot tear a line (pre-atomic `writeln!` issued two syscalls and a race tore two records onto one physical line on #2745). If a torn append still appears, readers normalize it via `split_torn_json` — the record file itself is never rewritten; the anti-tamper line holds.
- Record who/what requested each transition.
- Independent verification: QA-Expert-authored tests executed by the Tester, never agent-authored tests grading agent work.

### Loop guards (subagent tool-loop hardening, #2694)

The state machine defends the pipeline against agents that loop on a tool call instead of acting.
Two guards live in `pipeline-state.rs`. V2 has no `doom_loop` permission action, so they replace
the V1 `doom_loop` recovery layer (see `permissions.md` "Loop mitigation"):

- **`context`-read streak guard:** the `context` action refuses a streak of ≥ `CONTEXT_READ_STREAK_LIMIT` (8)
  consecutive reads with no intervening state-machine activity by that actor, printing a directive to
  stop re-reading and act. Any non-read event (a write, transition, block) resets the streak, so a
  legitimate agent is never throttled — only a pure read-loop is broken. (#2694: a planner spun 177
  context reads in ~2 minutes.) The limit is deliberately **above the largest same-role parallel
  dispatch wave**: N agents of one role each open with a context read, and no write event exists until
  the first of them acts, so N consecutive reads accumulate — limit 3 falsely blocked the 4th
  concurrent developer in #2893 wave 1 (staffing runs up to `ceil(points/5)` developers). A genuine
  loop still trips the guard quickly; the refusal event resets the streak.
- **A2A-file-as-comment refusal:** the `comment` action refuses any body file named `triage.md` (or
  carrying the `A2A working file` header marker) — planners edit the A2A file locally; the
  orchestrator assembles and posts the plan. (#2694: the raw template was posted as `Status`/`Question`
  comments three times.)
