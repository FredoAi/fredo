# Research Report: Plugin Architecture Precedents — How Mature Platforms Turn First-Party Modules Into Installable Extensions

**Agent:** Research Analyst (external standards / vendor specs / peer-reviewed literature)
**Date:** 2026-11-12
**Scope:** How established platforms structure installable UI extensions — manifest, isolation, API exposure, host↔plugin versioning, distribution/trust, and documented failure modes — and which parts of those models transfer to Fredo (Tauri v2 desktop, React 19 webview, Rust backend, in-tree `apps/ui/src/applications/*` registered at module load via `registerApplication()`).

## Executive Summary

1. **Adopt "declarative contributions + narrow imperative API," not "load my module and let it do anything."** Every mature system splits a plugin into (a) *static metadata* the host can read, validate and display without executing code, and (b) *code that only runs when activated*. VS Code `contributes` + `activationEvents` [VSC-1][VSC-2][VSC-4], Grafana `plugin.json` `extensions` block [GF-1], Raycast `commands[]` [RC-1], Figma `manifest.json` [FG-1], Obsidian `manifest.json` [OB-1] all follow this shape. This is the single most transferable pattern and it costs nothing to adopt.
2. **Make the manifest the security boundary you can actually enforce.** Figma's `networkAccess.allowedDomains` is a declarative egress allowlist enforced at runtime, with a CSP error on violation, and `["none"]` as a valid default [FG-1][FG-2]. Raycast's manifest-driven preference type `password` is how secrets are collected and stored [RC-1][RC-2]. Declared capability beats documented expectation every time.
3. **Activation/lazy-loading is a first-class requirement, not an optimisation.** VS Code's extension-host doc states the host exists so that "misbehaving extensions should not impact the user experience" and lists three concrete guarantees: no startup impact, no UI slowdown, no UI mutation [VSC-3]. JupyterLab's `autoStart: false` + `provides` token means a plugin is only instantiated when another plugin requires its service [JL-1]. Fredo's current registry is a module-load `push` — every app is in the initial bundle.
4. **Host↔plugin compatibility must be a declared, semver-checked range in the manifest — and the host must refuse to load outside it.** VS Code: `engines.vscode` is required, "Cannot be `*`", and controls which extension versions become available to which host builds [VSC-2][VSC-5]. Grafana: `dependencies.grafanaDependency` is required and validated with node-semver [GF-1]. Obsidian: `minAppVersion` **plus** a `versions.json` compatibility ladder so a host installs the newest compatible plugin version rather than the newest version [OB-2]. Fredo has none of this today.
5. **Version the *interface*, not just the package.** Grafana requires extension-point and exposed-component IDs of the form `{pluginId}/name/v1` and explicitly recommends the version suffix "to prevent future breaking changes" [GF-1]. OSGi makes versions and version *ranges* first-class in the manifest (`Export-Package ... version=`, `Import-Package ... version="[1.23,2)"`) and matches requirements to capabilities with a resolver [OSGi]. SemVer formalises the same contract: a public API must be *declared* before version numbers mean anything [SEMVER].
6. **Three isolation tiers are in production use, and each buys something different.** (a) *Separate process / own JS realm*: VS Code Extension Host [VSC-3], Theia's plugin host (dedicated process per frontend connection) [TH-1], Raycast (one child Node process; a v8 isolate + worker thread per extension with limited heap) [RC-2]. Buys crash containment and immunity to UI/startup damage. (b) *Two-realm split*: Figma runs plugin logic in a sandbox with **no browser APIs** and renders UI in an `<iframe>`, communicating by message passing [FG-2]. Buys a hard capability boundary while still allowing arbitrary HTML. (c) *Same realm, signing only*: Grafana loads frontend plugins into the same page and instead verifies a PGP signature over a SHA-256 file manifest at startup [GF-2][GF-3]. Buys supply-chain integrity, not runtime containment.
7. **Unsigned ⇒ not loaded is a defensible default, and Grafana ships it.** Grafana documents five signature statuses (Core, Invalid, Modified, Unsigned, Signed); an unsigned plugin "Grafana neither loads nor starts", and the only escape is an explicit `allow_loading_unsigned_plugins` setting that logs a warning [GF-3]. A documented developer-mode exception keeps the ergonomics survivable [GF-2][GF-3].
8. **Compile-time plugins are cheap to *build* and impossible to *ship* — that is the central tradeoff.** Backstage plugins are NPM packages discovered by scanning the app's dependencies during Webpack compilation [BS-4]; JupyterLab calls this class "source extensions" and marks developing them **deprecated**, because installing one "requires a user to rebuild JupyterLab" and needs Node.js [JL-1]. A shipped desktop binary can never rebuild itself, so Fredo cannot use *either* model verbatim — but note the split: JupyterLab's *prebuilt* half does **not** rebuild the host and **is** available to Fredo (see "What transfers").
9. **Prebuilt federated ESM is the workable middle path, and JupyterLab documents both its win and its cost.** Prebuilt extensions "can be loaded into JupyterLab without rebuilding JupyterLab", install per-user on system-wide deployments, and take precedence over a same-named source extension [JL-1]. The cost is real: dependency deduplication becomes a *manifest problem* — `sharedPackages` with `bundled` / `singleton` / `strictVersion` flags, because "the Lumino widgets system ... requires all packages use the same copy" and "tokens identifying plugin services also need to be shared" [JL-1].
10. **Service tokens (identity objects) beat string service names — but only where you have a type system.** JupyterLab uses `new Token(...)` instances rather than strings "to prevent conflicts between identifiers and to enable type checking" [JL-1]. Backstage uses `createExtensionDataRef` + `createApiRef` with the same motivation, and forbids duplicate or overly-generic data refs [BS-2]. TypeScript types are erased at runtime, so the *runtime* identity must still be a unique string — treat the token as sugar over a namespace, not as the guarantee.
11. **Ship a per-extension error boundary and a per-extension disable switch before you ship a single third-party plugin.** Backstage wraps extensions in `ExtensionBoundary` with `Suspense` + `ErrorBoundary` so "the error can be isolated & it would prevent the rest of the plugin to crash" [BS-2]. JupyterLab added per-*plugin* enable/disable and admin *locking* in 4.1 after users had no way to isolate a broken plugin [JL-2]. Grafana has `plugin.json.state: alpha|beta|stable|deprecated` plus per-plugin disable [GF-1].
12. **Overriding first-party behaviour needs an explicit, declared mechanism — or your plugins will fork core.** JupyterLab: `jupyterlab.disabledExtensions` lets an extension that replaces a core plugin auto-disable the original, replacing `@jupyterlab/filebrowser-extension:share-file` [JL-1][JL-3]. Backstage: `plugin.withOverrides()` + `getExtension('page:catalog').override({ factory })` [BS-1]. VS Code: `extensionDependencies` / `extensionPack` for composition, not replacement [VSC-2].
13. **Documented failure modes cluster into five buckets, and every one of them is a schema decision.** (i) host-version drift breaks plugins → JupyterLab ships a per-release "Extension Migration Guide" listing every renamed plugin ID, moved token, and removed API, and warns "Your extensions may break with new releases" [JL-1][JL-2]; (ii) duplicate/generic identity collides → Backstage duplicate ID is an error or silent override [BS-1][BS-2]; (iii) dependency duplication forks singletons → JupyterLab `sharedPackages` [JL-1]; (iv) unsigned/tampered code → Grafana `Modified signature` status [GF-3]; (v) unbounded egress → Figma `networkAccess` [FG-1].
14. **Fredo's biggest risk is not sandboxing — it is freezing its internal contracts too early.** Fredo's own tree shows rapid, structural internal churn (v1→row-native delivery in #2788, settings-shell retirement in #2868, per `docs/ENGINEERING_RULES.md`). Publishing `FredoApplicationClass`, `useEventRows`, the row store, and the dispatch surface as *public* API today would convert every future refactor into a breaking ecosystem change. Publish a small, versioned host facade and keep everything else private until it has survived at least one release cycle.

## Per-Precedent Sections

### 1. VS Code — the reference implementation of "manifest + lazy activation + separate host"

**Manifest / package format.** `package.json` at the extension root. Required: `name`, `version` (SemVer), `publisher`, `engines` (must contain `vscode`, "Cannot be `*`"), plus `main` (Node entry) and/or `browser` (web-worker entry). Notable optional fields: `activationEvents[]`, `contributes{}`, `extensionDependencies[]`, `extensionPack[]`, `extensionKind[]` (`ui` / `workspace`), `capabilities.untrustedWorkspaces` (`supported: true \| false \| 'limited'`, `restrictedConfigurations[]`), `pricing`, `sponsor` [VSC-2][VSC-3][VSC-6]. Packaging is `.vsix` via `vsce`; the same command publishes to Marketplace [VSC-5]. Extension identity is `<publisher>.<name>` and is permanently reserved once used [VSC-5].

**Isolation model.** The Extension Host is a distinct process (Node) or a browser Web Worker (`browser` entry). Its stated purpose is that "misbehaving extensions should not impact the user experience", and it prevents extensions from: impacting startup performance, slowing UI operations, modifying the UI [VSC-3]. `extensionKind` decides whether an extension runs locally (`ui`) or where the workspace is (`workspace`) — a *placement* control orthogonal to isolation [VSC-3].

**API exposure.** A single `vscode` module is injected into `activate(context: ExtensionContext)`; everything is acquired from `context` and disposed via `context.subscriptions` [VSC-1]. Types come from `@types/vscode`, whose version is pinned by `engines.vscode` [VSC-1]. Unstable surface is partitioned as *proposed APIs*: available only in Insiders, must not be published, enabled via `enabledApiProposals` in the manifest, and historically graduated into stable API [VSC-7].

**Versioning / compatibility.** Distribution is gated by `engines.vscode`; a `^1.9.0` requirement means only hosts ≥1.9.0 receive that extension version, so Stable users get the update when Stable reaches 1.9.0. Date-pinned builds (`^1.56.0-20210428`) are supported from 1.57 [VSC-5]. Pre-release extensions are a separate axis: `--pre-release`, distinct version numbers, and the recommended even/odd-minor convention because "semver pre-release tags are **not supported**" [VSC-5].

**Distribution & trust.** Marketplace publisher identity (Azure DevOps), optional DNS-TXT `verified publisher` badge after a 6-month track record, and publishing credentials moving from long-lived PATs to OIDC/Entra federated identity (PATs retired 2026-12-01) [VSC-5]. No code signing of `.vsix` contents is documented; VS Code instead builds *execution consent* into the product via **Workspace Trust**: the default for an extension that declares nothing is "not supported in Restricted Mode" and it is disabled; `'limited'` lets an extension gate trust-sensitive features on `workspace.isTrusted` and strips `restrictedConfigurations` values from untrusted workspaces [VSC-6].

**Documented failure modes.** (i) Startup cost → hence activation events, with `*` explicitly discouraged and `onStartupFinished` offered as the non-blocking alternative [VSC-3][VSC-4]. (ii) Supply-chain in docs: `vsce` refuses user-provided SVG icons/badges and requires https image URLs [VSC-5]. (iii) Namespace squatting/impersonation: removed extension names stay permanently reserved [VSC-5]. (iv) Publishing leaks from old PAT scopes → the entire PAT path is being retired [VSC-5].

### 2. Eclipse Theia — four extension tiers, and an honest warning about one of them

**Manifest / package format.** Two shapes. *Theia extensions* are npm packages with `keywords: ["theia-extension"]` and a `theiaExtensions[]` array mapping `frontend`/`backend` to compiled JS modules that export Inversify `ContainerModule`s [TH-2]. *VS Code extensions* use VS Code's `package.json` verbatim, since Theia implements the same extension API [TH-1].

**Isolation model.** Four complementary mechanisms, explicitly documented as having different costs [TH-1]:
- *VS Code extensions / Theia plugins*: "run in a dedicated process per frontend connection", installable at runtime, restricted to the VS Code API.
- *Theia plugins*: same architecture + extra Theia-only frontend APIs; the docs say support is **under discussion** and recommend against them.
- *Headless plugins*: a dedicated backend process per application, no frontend access, no default backend-service API — only what the app publishes.
- *Theia extensions*: **compile-time**; they "become a core part of your Theia application" and "can access the full API of Theia."
This is the most explicit statement in any surveyed doc that *isolation level is a product decision with a capability cost*.

**API exposure.** Dependency injection against `*Contribution` interfaces (`CommandContribution`, `MenuContribution`, …). Cross-process calls are typed proxies: the backend binds an `RpcConnectionHandler` on a path; the frontend obtains `connection.createProxy<TaskServer>(taskPath, client)`; all handlers are multiplexed over one WebSocket by `MessagingContribution` [TH-3].

**Versioning / compatibility.** npm semver on the package; no Theia-specific host-range field is documented for native extensions (they are compiled into a specific app) [TH-2]. For VS Code extensions Theia inherits `engines.vscode` and publishes a compatibility matrix against VS Code's API surface [TH-1].

**Distribution & trust.** Open VSX by default; `VSX_REGISTRY_URL` points the backend at a private registry or caching proxy, and an "OVSX router" can target multiple registries [TH-1]. That is an unusually good pattern for an enterprise desktop app: a first-party-signed registry with a documented allowlist of mirrors.

**Documented failure modes.** The docs themselves flag two: the Theia-plugin tier is unstable ("support ... currently under discussion"), and VS Code extensions are "limited to the VS Code extension API" so "some use cases [are] not possible" — i.e., tier choice is a hard ceiling, discovered late [TH-1]. (The dedicated `authoring_plugins` page now opens with a deprecation notice and recommends VS Code extensions or Theia extensions instead [TH-4].)

### 3. JupyterLab — prebuilt federated ESM, and the true cost of deduplication

**Manifest / package format.** npm `package.json` with a `jupyterlab{}` object: `extension` (bool or module path), `mimeExtension`, `themePath`, `schemaDir` (settings JSON-schema directory), `disabledExtensions[]`, `sharedPackages{}`, `discovery{}` (companion kernel/server packages for pip/conda), and for prebuilt builds `outputDir` and an experimental `webpackConfig` [JL-1].

**Isolation model.** **None at the process level.** A plugin is a JS object in the host page; "MIME renderer plugins" are explicitly "more declarative and more restricted" and are auto-converted into application plugins [JL-1]. So JupyterLab's safety story is *API narrowness + distribution controls + an admin lock*, not sandboxing.

**API exposure.** The `JupyterFrontEnd` application object (`commands`, `docRegistry`, `shell`, `serviceManager`, `restored`) passed as the first `activate` argument; further capabilities are requested by **Token**. `requires` = hard dependency (throws, plugin not activated); `optional` = `null` if absent; `provides` registers the return value of `activate` as the service. Activation is ordered so providers start before consumers, and a token may be registered only once [JL-1][JL-4]. The docs deliberately use object tokens **instead of strings** "to prevent conflicts between identifiers and to enable type checking" [JL-1].

**Versioning / compatibility.** Plugin ID convention `<package>:<plugin>`; release-by-release "Extension Migration Guide" enumerating renamed plugin IDs, moved tokens, and removed classes; the guide recommends publishing a **new major version of your extension per major JupyterLab version** and "setting an upper bound on the version of JupyterLab your extension is compatible with" [JL-1][JL-2]. Prebuilt extensions win over a same-named source extension [JL-1].

**Distribution & trust.** Prebuilt bundles ship inside pip/conda packages (or any directory copy) under `share/jupyter/labextensions/<pkg>`; the server serves `static/` via `/labextensions/`; an optional `install.json` records `packageManager`/`packageName`/`uninstallInstructions` so the host can tell the user how to remove it [JL-1]. No signing is documented. Per-plugin enable/disable was added in 4.1, and pre-existing disabled plugins were automatically **locked** on first start "to ensure that there is no change to user-exposed functionality" [JL-2].

**Documented failure modes.** (i) Rebuild requirement: source extensions need Node.js, "may take a lot of time and memory, so some users may not be able to install" — the documented reason prebuilt exists and source development is deprecated [JL-1]. (ii) Dependency forking: `@lumino/widgets` "requires all packages use the same copy", and tokens must be shared → `sharedPackages.{bundled,singleton,strictVersion}` [JL-1]. (iii) Global CSS leakage: from 4.3, styles are scoped and extensions must annotate out-of-shell DOM with `jp-ThemedContainer` — a breaking change for plugin authors [JL-2]. (iv) Silent ID drift: the migration guide lists plugin IDs that moved *packages* between releases (e.g. `@jupyterlab/help-extension:licences` → `@jupyterlab/apputils-extension:licenses-*`) [JL-2].

### 4. Backstage — the extension *tree*, and what compile-time buys and costs

**Manifest / package format.** A plugin is an npm package whose default export is `createFrontendPlugin({ pluginId, title?, icon?, extensions[], routes?, externalRoutes?, featureFlags?, if?, info? })`. Exactly one plugin instance per package. `info.packageJson` is **mandatory** for plugins in their own package; `info.manifest` is restricted to single-organization plugins [BS-1][BS-3]. Each extension may declare a `configSchema` (Standard Schema, e.g. zod v4) that validates and defaults `app-config.yaml` values — and "it is not possible to provide a default configuration... this must instead be done through defaults in the configuration schema" so configurations replace rather than merge [BS-2].

**Isolation model.** **None at runtime.** Plugins are discovered by scanning the app's dependencies *during Webpack compilation* and bundled in [BS-4]. The only fault isolation is React-level: `ExtensionBoundary` provides `Suspense` (lazy load with fallback), `ErrorBoundary` (fallback component so "the rest of the plugin" does not crash), and an `AnalyticsContext` carrying `extensionId`/`pluginId` [BS-2].

**API exposure.** An **extension tree**. Each node declares `output` (a list of `ExtensionDataRef`s) and `inputs`; a child attaches to a parent via `attachTo: { id, input }` (or a typed `parent.inputs.children` reference) and its output becomes the parent's input. `createExtensionDataRef<React.JSX.Element>().with({ id })` gives a typed, uniquely-identified slot; repeating the same ref in `output` "will conflict ... and cause an error", and "overly generic extension data references are a bad idea" [BS-2]. Cross-cutting services use `createApiRef`/`ApiBlueprint`/`useApi`; navigation uses `createRouteRef` and `externalRoutes` binding [BS-1][BS-3].

**Versioning / compatibility.** One plugin instance per `pluginId` per app; duplicate IDs "will either result in an error or one of the extensions will override the others" [BS-1]. `if` predicates (feature flags, permissions) are evaluated "when the app tree is prepared, not continuously", so changing them "typically means reloading the app"; a permission check that 5xx/network-fails is retried at 0.5/1/2/4/8s, and if it still fails "the app fails to start with `Failed to authorize extension permissions`" [BS-2]. There is no host-version range field — the host *is* the build.

**Distribution & trust.** npm / your monorepo; no signing, no review, no sandbox. Security posture is "you build it, you own it". Notably, `pluginOverrides` in `app-config.yaml` lets an org re-attribute third-party plugin metadata (owner, links) without forking — an ownership-override pattern worth copying [BS-4].

**Documented failure modes.** (i) Ordering surprises: enabling a disabled extension "resets the ordering ... pushing it to the end of the list", with the recommendation to ship order-sensitive extensions disabled by default [BS-2]. (ii) Attachment mismatch: attaching an extension to an input that requires data it does not output is "an error"; the tree cannot contain cycles [BS-2]. (iii) Startup cost: factories "should be lean and not do any heavy lifting or async work" because they run during app init [BS-2]. (iv) Config semantics: whole-object replacement rather than merge, so partial config objects silently reset fields [BS-2].

### 5. Grafana — signing as the trust model, and an optional native sidecar

**Manifest / package format.** `plugin.json` is mandatory; Grafana "mounts every folder that contains a `plugin.json` file unless the folder contains a subfolder named `dist`", in which case `dist` is mounted [GF-1]. Required: `id` (pattern `^[0-9a-z]+-([0-9a-z]+-)?(app|panel|datasource)$`), `type` (`app|datasource|panel|renderer`), `name`, `info` (with required `keywords`, `links`, `logos`, `updated`, `version`), `dependencies` (with required `grafanaDependency`, validated by node-semver) [GF-1]. Optional but load-bearing: `backend: true` + `executable` (resolved as `<executable>_<$GOOS>_<$GOARCH>`), `includes[]` (dashboards/pages/panels with `role`/`action`/`addToNav`), `routes[]` (proxy with header/token/JWT injection), `iam.permissions[]` (`action`, `scope`) + `roles[]` for RBAC, `state` (`alpha|beta|stable|deprecated`), `preload`, and the `extensions` block [GF-1].

**Isolation model.** Frontend plugin code runs in the Grafana page (same origin). The *backend* half, when present, is a separate OS process launched from the `executable` naming convention [GF-1]. So the isolation boundary exists exactly where native code exists — and the security control everywhere is signing, not sandboxing.

**API exposure.** `@grafana/data` + `@grafana/runtime` packages. UI surface is **extension points**: named slots with IDs of the form `{pluginId}/name/v1`; a plugin registers `addedComponents`/`addedLinks`/`addedFunctions` by `targets[]`, and may `exposeComponent` for other plugins to consume, also `{pluginId}/name/v1`. The manifest must list every registration or "components that are not listed here won't work" [GF-1]. Backend access to Grafana itself is mediated by a service account whose bearer token is injected as `GF_PLUGIN_APP_CLIENT_SECRET` [GF-1].

**Versioning / compatibility.** `grafanaDependency` semver range gating; version-suffixed extension-point IDs; and a *published per-major migration guide set* (6→7 through 13.1→13.2) that plugin authors are expected to follow [GF-1][GF-5]. Also: AngularJS→React migration is documented as "release it under a new major version" with no standard automated path — the honest cost of a framework-level API change [GF-4].

**Distribution & trust.** Every plugin must be cryptographically signed to be accessible; at startup Grafana verifies all plugins and classifies each as `Core`, `Invalid signature`, `Modified signature`, `Unsigned`, or `Signed`. If unsigned, "Grafana neither loads nor starts it" and logs `WARN ... is unsigned`. Escape hatches: `allow_loading_unsigned_plugins` (logged as `Running an unsigned plugin`) and a development mode that allows all unsigned plugins [GF-2][GF-3]. The signed artifact is `MANIFEST.txt`: a PGP-clearsigned message containing `manifestVersion`, `signatureType`, `signedByOrg`, `plugin`, `version`, `time`, `keyId`, and a `files{}` map of SHA-256 digests; Grafana holds the public key [GF-2]. Signature **levels** are a distribution policy: `Private` (own instance only, not catalog, not Cloud-compatible), `Community` (OSS/non-profit, catalog), `Commercial` (paid subscription to sign, catalog), `Grafana`/`Enterprise` (first-party), `Marketplace` (partner agreement, partner's own EULA) [GF-4]. The policy also forbids telemetry/analytics collection, requires encrypted credentials (`secureJsonData`), and forbids bundling multiple plugins into one [GF-4].

**Documented failure modes.** (i) Tampering is a *detected* state (`Modified signature`), not an assumed-away risk [GF-3]. (ii) Cross-platform signing bug: on Windows, backslashes in `MANIFEST.txt` break verification and must be rewritten to `/` "every time you sign" [GF-2] — a concrete example of why path normalisation must precede hashing. (iii) `rootUrls` is *required* for private plugins but is rejected before review for public ones, a confusing-but-documented failure [GF-2]. (iv) Framework migration is an ecosystem-wide breaking change requiring new majors [GF-4].

### 6. Raycast + Figma — the two most instructive permission models

Chosen over Obsidian because Raycast and Figma each demonstrate a *distinct, enforceable* permission posture, whereas Obsidian documents essentially none (its security documentation was not retrievable — see Sources note).

#### 6a. Raycast — typed manifest, review pipeline, narrow RPC

**Manifest.** `package.json` as a superset of npm's, so one file serves both build and store. Required: `name`, `title`, `description`, `icon`, `author` (store handle), `platforms[]`, `categories[]`. Structural fields: `commands[]` (`name` → entry file, `title`, `mode: "view"|"no-view"|"menu-bar"`, `interval` for background, `arguments[]`, `preferences[]`, `disabledByDefault`), `tools[]` (`name`, `title`, `description`, `functionalities`), `ai{}` (`skills[]` — Agent Skills with `SKILL.md`, `mcp{}` server config, `modelProvider`, `instructions`, `evals`), `owner`/`access: "public"|"private"`, `external[]` (excluded from the bundle but resolved at runtime), and typed `preferences` (`textfield`, `password`, `checkbox`, `dropdown`, `appPicker`, `file`, `directory`) [RC-1].

**Isolation.** Raycast launches "a **single child Node.js process** where extensions get loaded and unloaded as needed"; each extension "runs in its own **v8 isolate** (worker thread)" with its own event loop and "limited heap memory", explicitly "to ensure isolation between extensions when future Raycast versions may support background executions". IPC is "standard file handles and a thin RPC protocol that only exposes a **defined set of APIs**, that is, an extension cannot just perform any Raycast operation". The managed Node binary is downloaded by Raycast and its integrity verified [RC-2].

**API exposure.** Direct typed imports from `@raycast/api`; `LaunchProps` carries `arguments`, `launchType`, `draftValues`, `fallbackText`, `launchContext`. Commands unload entirely from memory when popped, with a documented memory limit that terminates the command and shows an error [RC-5].

**Versioning.** No host-range field. The strategy is instead aggressive auto-update of both app and extensions, framed as a security feature: "we minimize the time from update to distribution" [RC-2].

**Trust.** All extensions are open source in a public repo; Raycast + community review against store guidelines, then CI validates manifest schema, asset formats, author validity, and build/type errors; the built artifact is archived and uploaded to the store [RC-2]. Explicit prohibitions: no Keychain Access; no external analytics; no opaque binaries; background-downloaded binaries must come from a server the author does not control, with hash integrity checks; `MIT` license required [RC-3]. Runtime permissions are **not** further sandboxed for fs/network — the doc says so plainly [RC-2].

**Failure modes.** (i) Heap limit kills commands → documented user-visible error [RC-5]. (ii) Hand-edited extensions diverge from the repo → `pull-contributions` is required or publish fails [RC-4]. (iii) Ambiguous ownership → extensions under an organisation are private unless `access` says otherwise [RC-1].

#### 6b. Figma — declarative egress + two-realm split

**Manifest.** `manifest.json` with `name`, `id` (assigned by Figma, used to publish updates), `api` (API version string), `editorType[]` (`figma|figjam|dev|slides|buzz`), `main`, `ui` (string or map → `__html__` / `__uiFiles__`), `documentAccess: "dynamic-page"` (**required** for all new plugins), `networkAccess{allowedDomains[], reasoning?, devAllowedDomains[]}`, `permissions[]` (`currentuser|activeusers|fileusers|payments|teamlibrary`), `capabilities[]` (`textreview|codegen|inspect|vscode`), `menu`, `parameters[]`, `relaunchButtons[]`, `enableProposedApi` (dev only), `enablePrivatePluginApi`, `build` (experimental) [FG-1].

**Isolation.** Two realms. Plugin logic runs "on the **main thread in a sandbox**" that "**does not expose browser APIs**" — no `XMLHttpRequest`, `fetch`, `setTimeout`, or DOM — while UI runs in an `<iframe>` created by `figma.showUI()` with full browser APIs. "The main thread can access the Figma 'scene' ... but not the browser APIs. Conversely, the iframe can access the browser APIs, but not the Figma scene. The main thread and the iframe can communicate ... through **message passing**" [FG-2]. When `networkAccess` is set, out-of-allowlist requests are blocked and return a CSP error; `["none"]` is a valid total-deny value [FG-1][FG-2].

**API exposure.** The `figma.*` global inside the sandbox; HTML delivered as a string constant, not a file the plugin can fetch. The scene graph is reachable only through the sandbox's `figma` object [FG-1][FG-2].

**Versioning.** `api` is a per-plugin pinned version; Figma explicitly "don't auto-upgrade the api version of plugins to give you the chance to test your plugin against the new version" [FG-1]. `documentAccess: "dynamic-page"` is a one-way migration with its own doc, and its absence changes runtime behaviour (extra page loads) rather than failing hard [FG-1].

**Trust.** Store review + published review guidelines; the effective network allowlist is displayed publicly on the plugin's community page, so the permission is socialised, not just enforced [FG-1].

**Failure modes.** (i) Ambient authority: docs warn plugins must call `figma.closePlugin()` or "the plugin runs indefinitely and the user sees a 'Running …' toast" [FG-2]. (ii) Performance cliffs in large documents (frozen plugins, page loading) are documented as author-side responsibilities [FG-3]. (iii) Egress allowlists do **not** cover resources loaded by a rendered website — an explicitly documented limitation [FG-1].

#### 6c. (Reference only) Obsidian — what *not* to copy, and one thing to copy

Obsidian's plugin runs in the app with `require('obsidian')`, `require('fs')`, and `require('electron')` available, with `isDesktopOnly` marking plugins that need Node/Electron [OB-1]. No sandbox and no signing are documented. **Reject the privilege model.** But copy `minAppVersion` + `versions.json`: when the manifest demands a newer app than the running one, "your `versions.json` will be consulted to find the latest version of your plugin that is compatible", and installation then pulls `manifest.json`, `main.js`, and optionally `styles.css` from a GitHub release tagged with that version [OB-2]. Also copy the *teardown* discipline: `registerEvent` / `registerDomEvent` / `registerInterval` exist so the host auto-detaches handlers on unload [OB-1].

## What Transfers to a Rust+React Desktop Host, and What Does Not

### Transfers cleanly (low cost, high value)

1. **Static manifest with declared contributions + activation rules.** Fredo already has the raw material: `FredoApplicationClass` declares `id`, `name`, `icon`, `render`, `gridConfig`, `showable`, `isMultiWindow`, `hasSettings`, `renderSettings` (`apps/ui/src/shared/classes/FredoApplicationClass.ts:51-118`), and the registry is a module-load `push` (`applications/applicationRegistry.ts:34`). A `fredo.plugin.json` that mirrors those fields is a mechanical extraction, not a redesign. The `showable`/`hasSettings`/`renderSettings` trio is already a contribution-point vocabulary.
2. **Declared host-compatibility range + refusal to load.** `engines.vscode` [VSC-2][VSC-5], `grafanaDependency` [GF-1], `minAppVersion` + `versions.json` [OB-1][OB-2]. Fredo ships a Tauri binary that auto-updates on its own cadence; without this field, every plugin update is a silent compatibility gamble. The `versions.json` ladder is one JSON file and it prevents the worst support burden in the whole model.
3. **Versioned interface identifiers.** Grafana's `{pluginId}/name/v1` for extension points and exposed components [GF-1]. This is the cheapest form of interface versioning that actually works, and it composes with Fredo's existing kebab-case `id` convention.
4. **Narrow host facade object instead of ambient imports.** VS Code injects `vscode` [VSC-1]; Raycast exposes only "a defined set of APIs" over RPC [RC-2]. For Fredo the analogue is a single `FredoHost` object passed to a plugin's `activate(host)`: window verbs routed through the one `dispatch()` the engineering rules already mandate, `useEventRows` scoped to declared event types, `invoke` limited to an allowlisted command set, and a `context.subscriptions`-style disposal list. This is *compatible* with the existing rule that every channel funnels through one `dispatch()` — a plugin's declared surface becomes another declaration consumed by the same host.
5. **Per-extension error boundary + per-extension disable.** Backstage `ExtensionBoundary` [BS-2]; JupyterLab plugin manager + admin locks [JL-2]. In React 19 this is a `<PluginBoundary>` with an error boundary and a lazy `import()`. Combined with a persisted disabled-set, this is the difference between "plugin broke, disable it" and "app broke, reinstall".
6. **Declared egress allowlist.** Figma's `networkAccess` [FG-1]. Tauri v2 has real teeth here: the Rust side can scope HTTP to a manifest-declared host list and surface violations as transport errors. Declaring `["none"]` as the default is the single highest-leverage security decision available.
7. **Signed bundle + "unsigned ⇒ not loaded" with a dev-mode escape.** Grafana's `MANIFEST.txt` (PGP clearsign over `files{}` SHA-256) is directly implementable with existing Rust crates, and the status vocabulary (`Core`/`Signed`/`Unsigned`/`Modified`/`Invalid`) is a ready-made UX [GF-2][GF-3]. Copy the *statuses* and the *default-deny*; do not copy the PGP-key-in-the-binary operational burden without a key-rotation story.
8. **Manifest-recorded uninstall provenance.** JupyterLab `install.json` (`packageManager`, `packageName`, `uninstallInstructions`) [JL-1]. When a plugin arrives as a directory copy rather than through a manager, the host still needs to tell the user how to get rid of it.
9. **Per-plugin settings schema.** JupyterLab `schemaDir` + `jupyter.lab.*` settings keys [JL-1][JL-4]; Backstage per-extension `configSchema` with replace-not-merge semantics [BS-2]. Fredo already has `renderSettings()` and a settings surface; a JSON-Schema-driven settings section is the natural generalisation.
10. **Declared dependency sharing.** JupyterLab `sharedPackages.{bundled,singleton,strictVersion}` [JL-1]. Fredo's equivalent singletons are React 19 + Chakra + the row store + the theme tokens. A plugin that bundles its own React will produce exactly the "two copies of the framework" failure JupyterLab documents.

### Transfers with real cost (do it only if the threat model demands it)

11. **Separate extension-host process (VS Code).** [VSC-3] The guarantee it buys — an extension cannot impact startup, cannot slow the UI, cannot modify the UI — is genuinely strong. The cost for Fredo is severe and asymmetric: you would need (a) a process supervisor in Rust, (b) a serialisable API shim for every host capability a React app uses, (c) an IPC transport with reconnection and backpressure, (d) a second copy of the entire UI framework in the child (React + Chakra + theme), and (e) a way to composite a child-rendered surface into the host DOM. Note that VS Code pays this cost because extensions are **Node** code that must touch the filesystem and language servers; most of Fredo's applications are *pure UI over rows the host already delivers*. Paying the full VS Code price to sandbox a component that only reads `useEventRows` is a bad trade.
12. **`iframe` realm split (Figma).** [FG-2] This is the cheapest *real* sandbox for third-party UI: the sandbox gets no host JS, and the host can enforce CSP inside the frame. The cost is precisely what Figma documents — the two realms need message passing, and the plugin loses the host's Chakra context, theme tokens, focus routing, and keyboard surface unless you explicitly bridge all four. For Fredo, whose engineering rules make the *declared keyboard surface* and *theming tokens* load-bearing, an iframe plugin cannot participate in `validateSurface()`/`dispatch()` without a bridge that reimplements them. Verdict: viable for "opaque third-party panel" plugins, wrong for "first-class application" plugins.
13. **Native sidecar + signed frontend (Grafana).** [GF-1][GF-2] Grafana's `backend: true` + `executable_<os>_<arch>` + signing is the closest structural analogue to what Fredo would actually need if a plugin requires Rust-side capability: ship a signed binary, launch it as a managed child, talk a narrow protocol. Fredo already has precedent for a managed sidecar (`llama-server`, per `docs/ENGINEERING_RULES.md`), so the *operational* shape is known. The cost is per-platform builds and notarisation.

### Does **not** transfer

14. **Build-time federation with a host rebuild (JupyterLab source extensions / Backstage Webpack discovery).** [JL-1][JL-2][BS-4] Not because federation is bad, but because *rebuilding* is impossible: a distributed Tauri binary cannot be recompiled on a user's machine, and shipping a Node toolchain to end users is exactly the failure JupyterLab deprecated. **However**, note the crucial distinction: JupyterLab's *prebuilt* extensions do **not** rebuild the app — the host ships a federation runtime and loads `remoteEntry.<hash>.js` from disk [JL-1]. That half *is* available to Fredo: vendor a federation runtime into the shipped bundle once, define the shared singletons as `strictVersion`-pinned host modules, and load plugin bundles at runtime. The thing Fredo cannot copy is the *source-extension* install path, not the runtime.
15. **Dependency-injection container as the extension mechanism (Theia).** [TH-1][TH-2] `inversify` `ContainerModule`s give full-internals access and excellent composition for a *compile-time* platform, but they bind a plugin to the host's object graph. Fredo is React-function components, not DI classes; forcing a container to get extension points buys nothing and freezes the internals.
16. **Full-privilege same-realm loading (Obsidian).** [OB-1] Not acceptable for third parties, and unnecessary for first-party because first-party code is already in-tree. This is the one model to reject outright.
17. **Marketplace-scale identity/billing infrastructure.** VS Code's Azure DevOps publisher + verified-DNS badge [VSC-5] and Grafana's five signature levels + paid commercial signing [GF-4] are business infrastructure, not architecture. A new desktop app with an empty ecosystem gains nothing from a `Commercial` tier and loses a lot from the friction.
18. **"Auto-update and never expose versions" (Raycast).** [RC-2] Raycast can auto-update one app and its store together because it is a single-vendor, always-online launcher. Fredo's plugins will be built by third parties against a host that lags; the `minAppVersion`+`versions.json` ladder is strictly better here.

### The blunt summary

VS Code's separate extension host and JupyterLab's build-time federation have **opposite** cost shapes, and neither is right for Fredo. VS Code pays a large, fixed, permanent engineering cost (a second runtime + a whole API shim) to buy process isolation, because its extensions are Node programs that need the filesystem. JupyterLab's *source* path pays a per-*install* cost (a rebuild) to avoid shipping a federation runtime, and it lost: that path is deprecated and prebuilt is the default exactly because users could not pay it [JL-1]. Fredo is a shipped binary whose "plugins" are, by construction, React components over typed rows. The structurally correct choice is **JupyterLab's prebuilt-federation half + Grafana's signing + Figma's declared egress + Backstage's error boundary**, i.e. runtime-loaded ESM, no host rebuild, host-owned singletons, declared capabilities, signed bundles, per-plugin isolation of *failures* — not of *privilege*.

## Recommendations, Ranked by Confidence

**R1 — Highest confidence. Publish a declarative manifest and keep it as the only install-time artifact.** `fredo.plugin.json` declaring: `id`, `name`, `version`, `host` (semver range), `kind` (`application|panel|command|theme`), `entry` (ESM URL), `contributes` (windows/verbs/settings/theme tokens), `activation` (lazy triggers), `requires` (declared host modules including their singleton pins), `permissions` (`network: {mode: "none"|"allowlist", hosts[]}`), `state`, `icon`, `license`. Evidence: every one of the eight precedents separates static declaration from activated code, and the ones with the largest ecosystems (VS Code, Grafana, Raycast) make the manifest the reviewable, validatable unit [VSC-1][VSC-2][VSC-4][GF-1][RC-1][FG-1][OB-1]. Cost: one JSON schema, one validator, one settings row.

**R2 — Highest confidence. Add `host` range + `versions.json` compatibility ladder before the first third-party plugin ships.** Version mismatch is the most-documented ecosystem failure across the surveyed set: JupyterLab ships a migration guide *per release* and recommends an upper bound [JL-1][JL-2]; Grafana requires `grafanaDependency` [GF-1]; VS Code makes `engines.vscode` mandatory and forbids `*` [VSC-2][VSC-5]; Obsidian resolves to the newest *compatible* version via `versions.json` [OB-2]. Retrofitting this after plugins exist means every existing plugin is "unknown compatibility".

**R3 — High confidence. Expose one narrow `FredoHost` facade; keep `FredoApplicationClass` internals private.** Today `registerApplication()` accepts a class instance whose `render()` closes over arbitrary imports, and the registry hands out the live array (`applications/applicationRegistry.ts:34,40`). A third-party plugin loaded that way gets the whole module graph. The precedents are unanimous: `vscode` module + `context` [VSC-1], `JupyterFrontEnd` + tokens [JL-1], `ExtensionBoundary` + typed data refs [BS-2], a "defined set of APIs" over RPC [RC-2]. Confidence is high because it is also the *cheapest* — a facade is less code than what exists. Corollary: keep the facade's verbs routed through the existing single `dispatch()` and declared-surface machinery rather than adding a second binding source (which would violate the repo's own keyboard rule).

**R4 — High confidence. Ship per-plugin error boundary + disable/lock *with* v1 of the loader.** Backstage isolates render failures per extension [BS-2]; JupyterLab retrofitted per-plugin disable in 4.1 and had to auto-lock previously-disabled plugins to avoid changing behaviour [JL-2]. Retrofitting this after a bad plugin lands is a support incident. This is the "failure isolation" that a same-realm loader *can* deliver, and it covers the majority of realistic plugin harm (crashes, infinite loops, bad renders) without a process boundary.

**R5 — High confidence. Default-deny network with a declared allowlist.** Figma enforces `networkAccess` at runtime with `["none"]` valid [FG-1][FG-2]; Raycast's review forbids hidden egress and external analytics and requires hash-checked binaries from author-independent sources [RC-3]. Fredo has an advantage Figma lacks: Tauri's Rust side can enforce the allowlist below the JS layer, so a plugin cannot bypass it by reaching for a different API.

**R6 — Medium-high confidence. Sign bundles; classify `Unsigned`/`Modified`/`Signed`; do not load `Unsigned` by default.** Grafana's model is proven and the statuses are a ready-made UX [GF-2][GF-3]. The confidence is slightly lower than R1–R5 only because the *key management* (rotation, revocation, offline signing CI) is real operational work, and because a small first-party-only plugin set does not yet need it. Ship the status classification early; enforce default-deny as soon as a third party can publish.

**R7 — Medium confidence. Load plugins as prebuilt ESM with host-pinned singletons; never require a rebuild.** JupyterLab proves prebuilt works and documents the exact failure it prevents [JL-1]; it also documents the exact cost — `sharedPackages` because a duplicated UI framework or duplicated token breaks the app [JL-1]. Fredo's singletons are React 19, Chakra v3, the theme token set, the row store, and the `StreamContext` module instance. The confidence is medium because the module-federation runtime choice (Rspack federation vs a hand-rolled import map + `import()`) is an engineering decision not settled by any precedent here.

**R8 — Medium confidence. Declare an explicit override mechanism rather than allowing core patches.** JupyterLab `disabledExtensions` [JL-1][JL-3]; Backstage `withOverrides` [BS-1]. Without this, plugins fork core apps, and two live owners of one window id will collide with the registry's existing first-wins dedupe (`dedupeByApplicationId`, `applicationRegistry.ts:81`). Medium because "override" and "disable" must be designed against the current `id`-keyed dedupe semantics, which are already load-bearing for launcher indices.

**R9 — Lower confidence. Consider an `iframe` sandbox tier for genuinely untrusted UI, and only that tier.** Figma demonstrates it works [FG-2], but it costs theme context, focus routing, and keyboard-surface participation — all of which Fredo's engineering rules treat as invariants. Recommend scoping this to "opaque panel" plugins and explicitly excluding it from applications that must appear in the launcher and participate in navigation.

**R10 — Explicit rejection. Do not build a VS Code-style separate extension-host process now.** Evidence-backed rationale: its value is process isolation for Node code that touches the filesystem [VSC-3]; Fredo's UI plugins do not. If a plugin later needs native capability, copy Grafana's backend-sidecar shape [GF-1] rather than re-architecting the UI loader. Revisit only if third-party plugins demonstrably need arbitrary OS access.

## Open Questions (max 8)

1. **What is the smallest `FredoHost` that covers the existing in-tree applications?** Enumerate every `shared/*` import the 14 current applications make (row store, `useEventRows`, settings save, navigation, window system, toast, theme tokens). If that set is small (≲15 symbols), the facade is cheap. *Unverified — needs a repo-wide import audit.*
2. **Which module-federation runtime, if any?** JupyterLab uses Rspack/module-federation with `sharedPackages` flags [JL-1]. Options for Fredo: Rspack federation, a hand-rolled import map + dynamic `import()`, or per-plugin `<iframe>`. No precedent here settles it; needs a spike against the actual Vite/Tauri bundle.
3. **Does Tauri v2's hardened release CSP permit runtime `import()` of an asset from an app-data directory?** This is the single largest feasibility unknown for R7. The repo's own `webview-security-evidence` skill asserts a hardened production CSP — worth checking whether dynamic ESM from a plugin directory is compatible with it before designing the manifest.
4. **Signing key management.** Grafana holds a public key in the binary and rotates via its signing service [GF-2][GF-3]. For Fredo: who holds the private key, how is it rotated, can offline CI sign without embedding a secret in the repo? *(Blocker for R6.)*
5. **Do third-party applications need to appear in the launcher alongside first-party ones?** If yes, the `iframe` tier (R9) is out for them and they must run in the host realm — which makes R3's facade the only real boundary. If no, an `iframe` tier becomes viable. *Product decision, not a research finding.*
6. **How do plugin verbs compose with the declared keyboard surface?** Repo rules require every channel to funnel through one `dispatch()` with `validateSurface()`, and a collision *inside one declaration* is an error while two applications may share a key. A plugin-contributed surface must therefore be validated per-plugin at load and reported as a plugin error (not a host crash). The exact validation contract for a *third-party* surface is unverified absent reading `validateSurface()`.
7. **What is the `host` range granularity?** Semver on the app version (VS Code style) is simplest [VSC-2][VSC-5] but couples plugin compatibility to marketing releases; an explicit `apiVersion` integer (Grafana's `/v1` style [GF-1]) is cleaner but needs a policy for when it increments. No surveyed precedent uses both; Fredo likely needs both axes and no source here covers that combination.
8. **Does the existing row-pipeline contract leak host internals?** `useEventRows(eventType, args, options)` is already the sanctioned read API, but the row *shapes* (`ChatRow`/`ToolUseRow`/`AgentSessionRow`) are a classifier-internal schema in active evolution (the repo's rules cite #2788 re-derivation and shared `rtdb/attrs.rs` helpers). Whether these can be declared stable for third parties — or need a projected, plugin-facing row type — is unresolved and decides the size of R3. *Unverified.*
