# Research Report: Plugin Backend Contracts & Capabilities

**Date:** 2026-11-12
**Author:** Research Analyst (external technical research)
**Scope:** The *backend half* of installable third-party applications: how a Tauri v2 host safely exposes capabilities to untrusted plugin code, how to version those contracts, what a plugin package should contain, and how a plugin's declared persistent data is owned and migrated. Frontend rendering, marketplace UX, and the current Fredo application-data implementation are referenced only as the host substrate they must fit.
**Method:** Primary sources fetched and read (Tauri v2 official docs + docs.rs, W3C/WASI/WebAssembly Component Model specs, IETF RFCs, SemVer 2.0.0, protobuf language guide, JSON Schema/OpenAPI specs, MIT-hosted Saltzer & Schroeder 1975, MITRE CWE, vendor plugin manifests for VS Code/Grafana/Obsidian/Figma/Home Assistant/npm, minisign/Sigstore, sqlx). Every Tauri v2 behavioural claim below carries a fetched citation; nothing is asserted from memory. Blog/secondary sources are labelled as such; three intended sources 404'd and are recorded in `Open questions` rather than paraphrased. No product code was modified.

## Executive Summary (14 actionable bullets)

1. **Tauri's capability system guards the webview, not the plugin.** Capabilities "granularly enable and constrain the core exposure to the application frontend running in the system WebView". Tauri states plainly that "any code executed by the plugins or the application core has full access to all available system resources and is not constrained" — a compiled-in Tauri *plugin* is host-trusted code, not a sandbox. Third-party apps must therefore be kept **out of the Tauri plugin layer** and behind a contract. [Tauri-Security]
2. **A dynamically installed bundle *can* be restricted to specific commands — but only if the host severs the default.** Tauri's default is that "all commands that you registered in your app (using `invoke_handler`) are allowed to be used by all the windows and webviews of the app"; opting out requires `tauri_build::AppManifest::commands(...)`. Fredo's `build.rs` calls bare `tauri_build::build()`, so today every window may invoke every command. [Tauri-Capabilities] [fredo: apps/tauri/src-tauri/build.rs]
3. **Runtime-authored capabilities exist and are on by default.** `Manager::add_capability` + `CapabilityBuilder`, plus `impl<T: AsRef<str>> RuntimeCapability for T`, are gated on `dynamic-acl`, which is a **default feature** of `tauri` 2.12.5. This is the mechanism for granting an installed bundle a capability at install time without recompiling the host. [tauri-docs-add_capability] [tauri-features]
4. **Per-window targeting is the enforcement point you already have.** Capability `windows` matches by label or glob (Fredo's `default.json` uses `["main","terminal","doom","app-*"]`), `webviews` allows finer targeting, and a window in multiple capabilities has its boundaries **merged** — which is why a plugin window must not share a capability file with first-party windows. [Tauri-Capability] [fredo: capabilities/default.json]
5. **Do not put a plugin window in `app-*`.** Today `app-*` receives `core:default`, `core:window:allow-create`, `core:window:allow-close`, and event listen/emit. A capability is enforced at the origin boundary, and Fredo's own `application_data_*` commands take a **caller-supplied** `applicationId`, so any webview in that capability can read or delete *another* application's declared tables. That is the confused deputy, verbatim. [fredo: capabilities/default.json] [fredo: application_data/commands.rs] [CWE/ConfusedDeputy]
6. **Tauri v2 replaced v1's `allowlist` + `dangerousRemoteDomainIpcAccess` with capabilities + `remote.urls`.** v1 exposed a single global allowlist and a "dangerous" remote-IPC toggle; v2 scopes remote access per capability with `remote: { urls: [...] }` using URLPattern, and warns that Linux/Android cannot distinguish an embedded `<iframe>` from the window itself. [Tauri-V1-Config] [Tauri-Capabilities]
7. **Version the *contract*, not the app.** SemVer 2.0.0 requires that you "declare a public API" and maps MAJOR→incompatible, MINOR→additive, PATCH→fix. For a host↔plugin contract that means: MAJOR = removed/renamed command or field, or a changed meaning; MINOR = new command/optional field/new enum value; PATCH = bug fix with no wire change. [SemVer]
8. **Copy protobuf's two hardest rules even if you never use protobuf.** Field numbers "cannot be changed once your message type is in use" and "should never be reused"; deletion requires `reserved`. Field *names* are reserved too, because JSON/TextFormat serialize the name. This is the cleanest published discipline for evolving a persisted or streamed row schema. [Protobuf]
9. **`$schema`/`$id` (JSON Schema) and `openapi`/`info.version` (OpenAPI) anchor a contract document to a dialect and an identity.** `$schema` "applies to the entire document and must be at the root level" and does *not* propagate into `$ref`'d documents, which must declare their own. OpenAPI explicitly separates the *spec* version (`openapi`) from the *API* version (`info.version`). [JSONSchema-$schema] [OpenAPI]
10. **Adopt RFC 9413 over folk "be liberal in what you accept".** The IAB records that tolerating unexpected input causes *protocol decay* and "bug-for-bug compatible" ossification, and recommends *active maintenance*, **virtuous intolerance**, and deliberate **exclusion** of non-compliant implementations — all conditional on being able to update implementations. A plugin host can update; therefore reject unknown-major, don't guess. [RFC9413]
11. **Choose the sandbox by trust level, not by aesthetics.** For untrusted third-party native logic the only defensible options are (a) WASI 0.2/0.3 components over WIT, or (b) a sidecar process speaking JSON-RPC 2.0 over stdio. In-process Rust `dylib` plugins are disqualified: the Rust ABI "offers no stability guarantees", and `abi_stable`'s own scope is "plugin system (without support for unloading)". [WASI-Security] [Rust-ABI] [abi_stable]
12. **Both untrusted options have a real capability story.** WASI components start with "no ambient authority" and each capability "is a separate import, and the host instantiates the component with only the imports it has granted", statically inspectable in the binary. A sidecar inherits only what the host puts in its environment/stdin and can be scoped by Tauri's `shell:allow-spawn` arg validators. [WASI-Security] [Tauri-Sidecar]
13. **A manifest is a capability declaration, and the best examples say so in one field.** Figma's `networkAccess.allowedDomains` (with `"none"` and required `reasoning` for `"*"`), Grafana's `iam.permissions[{action,scope}]` and `roles`, and npm's `peerDependencies` (host-compat range — "only changes in the host package's major version will break your plugin") are the three patterns worth copying. [Figma-Manifest] [Grafana-plugin.json] [npm-package.json]
14. **Signature verification is a TOCTOU problem, not a crypto problem.** minisign's Ed25519 + prehashed signatures and Sigstore's Fulcio/Rekor keyless model both solve *provenance*; neither solves "verify path, then load path". Hash and load the **same open handle**, and bind the manifest (name, version, entrypoint) into a signed trusted comment to prevent downgrade — minisign's docs call this out explicitly. [minisign] [Sigstore] [CWE-367]

## Capability Exposure Matrix

Ratings are for *safety against a malicious plugin*, not for performance.

| Mechanism | Isolation | Versioning story | Dev ergonomics | Fit: untrusted third-party | Fit: first-party |
|---|---|---|---|---|---|
| **Tauri command allowlist (capabilities + permissions + scopes)** | **None against code.** Constrains *which commands a webview origin may invoke*; explicitly does not protect against "malicious or insecure Rust code", "too lax scopes", "incorrect scope checks in the command implementation", "intentional bypasses from Rust code", webview 0-days, or supply chain. [Tauri-Capabilities] | Permission identifiers are `<plugin>:<command>` strings; additive commands are additive permissions; there is no built-in contract-version field — versioning must live in the command payloads. [Tauri-Permissions] | Excellent: JSON/TOML files, autogenerated `allow-*`/`deny-*` per command via `AppManifest::commands`, `$schema` autocomplete. [Tauri-Learn-Plugin-Perms] | **Only as an *inner* fence.** Necessary but insufficient: it is the correct mechanism for "this window may call these 8 host commands", not for "this code may not read `~/.ssh`". | **Ideal.** This is exactly what first-party apps should use. |
| **Capability tokens (host-minted, unforgeable, attenuable)** | **Conceptual, not mechanical.** A token is "a communicable, unforgeable token of authority" referencing an object + rights; protection depends entirely on the host never accepting a forgeable name (path, id) in place of the token. [Wikipedia-Capability] [Wikipedia-OCap] | Token carries `version` + `scope` + `expiry` as signed claims; versioning unit is the token claim set. | Moderate: every API must take a handle instead of an id; more host code, fewer plugin footguns. | **Best fit for the *data* layer** — replaces `applicationId: String` with a handle the host resolves. | Good; also simplifies audit. |
| **Sidecar RPC (JSON-RPC 2.0 over stdio)** | **Strong practical isolation:** separate process, separate address space, no shared memory, crashes contained. JSON-RPC is "stateless… transport agnostic… over sockets, over http, or in many various message passing environments". [JSON-RPC] | Version the method set + params: `{"jsonrpc":"2.0","method":"v2/query", …}`; unknown method → `-32601 Method not found` is a *clean, spec-defined* failure, not a crash. [JSON-RPC] | Good for any language; worse for streaming (frame it yourself) and for hot reload. Tauri scopes spawn via `shell:allow-spawn` with exact arg lists / `validator` regexes. [Tauri-Sidecar] | **Recommended for native compute now.** Panics and OOM stay out of the host. | Overkill; adds IPC latency to code you already own. |
| **WASM host functions (WASI 0.2/0.3 components + WIT)** | **Strongest documented model.** "A component without a filesystem import cannot read files; a component without a network import cannot open sockets… regardless of what the host process itself is permitted to do." Each capability is a WIT import; the host instantiates "with only the imports it has granted". [WASI-Security] | **Native and best-in-class:** WIT package names carry semver (`wasi:clocks@1.2.0`), and `@since` / `@unstable` / `@deprecated` gates are validated at build time. [WIT] [WASI-Releases] | Steepest: toolchain per language, Canonical ABI, no threads by default. Rust/JS/Go/Python/C# have documented paths. [WASI-Releases] | **Recommended target for "real" untrusted plugins.** Deterministic capability surface, statically inspectable. | Good for portable extensions (e.g. a user script hook), not for host-integrated UI. |
| **Raw shared library (`libloading` / `.dll`/`.so`)** | **Zero.** Same address space, same user, same filesystem authority. `libloading` is "bindings around the platform's dynamic library loading primitives with greatly improved memory safety" — memory safety of the *handle*, not the plugin. [libloading] | **Worst.** Rust ABI "offers no stability guarantees"; `abi_stable` adds load-time layout checking but explicitly targets "a plugin system (without support for unloading)" to tolerate differing Rust versions. [Rust-ABI] [abi_stable] | Misleadingly easy (`Library::new` + `Symbol`), then every ABI change is a silent UB risk. | **Disqualifying.** A `.dll` is arbitrary native code execution. | Acceptable only behind an `abi_stable` interface crate with a pinned toolchain. |
| **In-process Rust trait objects (`Box<dyn Plugin>`, no FFI)** | **Zero (compile-time trusted).** No boundary at all. | Compile-time only; the crate graph is the contract. | Best possible. | **Never.** It is exactly today's first-party model. | **This is the current model, and it is correct for it.** |

**One-line reading:** the allowlist is a *fence around the webview*, capability tokens are *how you stop naming objects*, and WASI/sidecar are the only two *actual* trust boundaries available for third-party code.

## Principle → Rationale → Citation

Saltzer & Schroeder's eight design principles are used verbatim where they apply; capability theory supplies the rest.

| Principle | Rationale for a plugin host | Citation |
|---|---|---|
| **Fail-safe defaults** — "Base access decisions on permission rather than exclusion… the default situation is lack of access." | A plugin with no declared capability must get *nothing*, not "everything except a deny-list". Tauri's own default is the anti-pattern here: all `invoke_handler` commands are allowed to all windows unless explicitly narrowed. | [Saltzer-Basic] §I.A.3(b); [Tauri-Capabilities] |
| **Complete mediation** — "Every access to every object must be checked for authority." | Every row read, every command, every token redemption must re-check. "Proposals to gain performance by remembering the result of an authority check [must] be examined skeptically." Caching a plugin's `applicationId→allowed` decision at subscribe time is a violation. | [Saltzer-Basic] §I.A.3(c) |
| **Least privilege** — "Every program and every user… should operate using the least set of privileges necessary to complete the job." | A plugin should receive a capability *per table it declared*, not per database; per event type, not per stream. | [Saltzer-Basic] §I.A.3(f) |
| **Least common mechanism** — "Minimize the amount of mechanism common to more than one user." | Two plugins must not share a subscription registry slot, a token namespace, or a table-name namespace that lets one observe the other's fan-out. | [Saltzer-Basic] §I.A.3(g) |
| **Economy of mechanism** — "Keep the design as simple and small as possible." | The plugin-facing surface (commands, events, manifest fields) must be small enough to audit line-by-line; every optional field is future debt. | [Saltzer-Basic] §I.A.3(a) |
| **Open design** — "The design should not be secret… not depend on the ignorance of potential attackers." | The contract schema and the permission vocabulary are public; only the minting key and user consent are secret. | [Saltzer-Basic] §I.A.3(d) |
| **Separation of privilege** — a mechanism needing "two keys… is more robust and flexible than one that allows… only a single key". | Installing a plugin should require *both* a valid signature *and* explicit user consent for the declared capability set. | [Saltzer-Basic] §I.A.3(e) |
| **Psychological acceptability** — "the human interface [must] be designed for ease of use, so that users routinely and automatically apply the protection mechanisms correctly." | If a capability prompt is confusing, users click through it. Show "reads your Mission Monitor sessions", not `application_data.read:missions`. | [Saltzer-Basic] §I.A.3(h) |
| **No ambient authority** — a program may act only on objects it was explicitly given a reference to. | The whole reason WASI is defensible: "a Wasm module or component starts with no ambient authority and can only do what the host explicitly grants". | [WASI-Security]; [Wikipedia-OCap] |
| **Unforgeable references** — "a capability is a communicable, unforgeable token of authority… references an object along with an associated set of access rights." | A string `applicationId` is a *name*, not a capability — which is precisely why passing it across the boundary creates a confused deputy. | [Wikipedia-Capability] |
| **"Only connectivity begets connectivity"** | A plugin can only reach what it was handed at instantiation (`endowment`/`introduction`), never what it can name. | [Wikipedia-OCap] |
| **Attenuation** — "given one reference… create another reference for a proxy object with certain security restrictions, such as only permitting read-only access… *Deep attenuation*… typically by use of a *membrane*." | A read-only plugin gets an attenuated view of the table; the membrane is the host's query layer, not a flag the plugin passes. | [Wikipedia-OCap] |
| **Confused deputy** — a program "tricked by another program (with fewer privileges) into misusing its authority". Solved by "bundl[ing] together the designation of an object and the permission to access that object." | `application_data_write { applicationId, table }` is the compiler/`(SYSX)BILL` example line-for-line: the name crosses the boundary, the authority does not. | [Wikipedia-ConfusedDeputy] |
| **Virtuous intolerance** — "Choosing to generate fatal errors for unspecified conditions… can ensure that faults receive attention." | Reject unknown-major payloads loudly instead of best-effort parsing; silence is what ossifies a protocol. | [RFC9413] §5.1 |
| **Exclusion** — "Deliberate exclusion of problematic implementations is an important tool." | A plugin that cannot meet the current MAJOR is disabled with a clear error and an upgrade path, not half-run. | [RFC9413] §5.2 |
| **TOCTOU** — "checks the state of a resource before using that resource, but the resource's state can change between the check and the use". | Verify the signature of the bytes you are about to load, from one handle; never "verify file, then `Library::new(path)`". | [CWE-367] |

## Recommended Contract Layers

Four layers, each with **one** versioning unit and **one** compatibility rule. The host is the sole author of layers A and B; layer C is the third-party logic boundary; layer D is what the plugin owns but the host materializes.

### (a) UI ↔ host *data subscriptions* (the RTDB row stream)

- **What crosses:** an event type + declared args → a stream of `insert` / `update` / `remove` row deliveries, plus a per-query replay-completion marker (Fredo's existing shape). [fredo: rtdb/commands.rs]
- **Versioning unit:** the **row schema per event type**, identified as `fredo.row.<eventType>@<major>.<minor>`.
- **Compatibility rule:** strictly **additive-only within a MAJOR** — new fields may appear (consumers must ignore unknown fields), no field may be renamed, retyped, or removed, and `remove` remains the *only* deletion signal (eviction, never re-key). This mirrors protobuf's wire-safe set (add field / remove field-with-reserve / add enum value) and OpenAPI/Grafana treatment of additive evolution. [Protobuf] §Updating A Message Type
- **Why a schema identity and not just a number:** JSON Schema's `$schema` and `$id` are the only published way to make "which dialect is this document" machine-checkable, and `$schema` does not inherit across `$ref`. Give every row type a published `$id` and validate plugin-facing payloads against it at install time. [JSONSchema-$schema]
- **Hard rule:** a MAJOR bump of a row schema is a **new event type**, not a mutation of the old one. This is the same move WIT makes when a variant gains a case: "if we had to *add* a new case to `calc-error`, this would be a *breaking change* and require either a new major version or adding a second, distinct `variant`". [WIT] §Stabilization of a new feature

### (b) UI ↔ host *commands* (the request/response surface)

- **What crosses:** `invoke(command, args) → result | error`, with structured error codes.
- **Versioning unit:** the **command contract** — name, argument object, result object, error code set — versioned as `fredo.cmd.<area>@<major>.<minor>`.
- **Compatibility rule:** additive MINOR (new command, new *optional* argument, new error code the caller must tolerate), breaking MAJOR (rename, required argument, changed semantics). Deprecate for ≥1 MINOR before removal, per SemVer rule 7 ("It MUST be incremented if any public API functionality is marked as deprecated") and its FAQ ("at least one minor release that contains the deprecation"). [SemVer]
- **Enforcement detail:** namespace every plugin-facing command so the *command name itself* carries the major: `plugin_v2__query_rows`. Tauri permissions are string identifiers `<plugin>:<command>`, so an old permission simply stops matching a new name — no silent cross-major call is possible. [Tauri-Permissions]
- **Error contract:** model it on JSON-RPC's reserved range because it is the only widely-deployed, spec'd plugin-ish error envelope: `-32601 Method not found`, `-32602 Invalid params`, `-32603 Internal error`, with `-32000..-32099` reserved for implementation-defined server errors. [JSON-RPC] §5.1

### (c) Host ↔ *native plugin logic* (the third-party compute boundary)

- **What crosses:** a small, typed function set — e.g. `transformRows`, `onEvent`, `health`.
- **Versioning unit:** **one WIT package** `fredo:plugin@<major>.<minor>.<patch>` (WASI target), *or* one JSON-RPC method namespace `plugin/<major>/<method>` (sidecar target). Both are single, inspectable, versioned units.
- **Compatibility rule:** the WIT route gets semver + feature gates for free: package names carry a full semver ("An optional *version field*, specified as full semver"), and `@since(version)` promises "once applied to an item, the item is not modified incompatibly going forward (according to general semantic versioning rules)". [WIT] §Package Names, §Feature Gates
- **The sidecar route must reproduce that discipline by hand:** method prefix per major, `-32601` for an unknown method, and a `plugin/handshake` call returning `{contractMajor, contractMinor, capabilities}` that the host checks *before* any work. [JSON-RPC]
- **Why not an in-process dylib:** Rust's `extern "Rust"` ABI "offers no stability guarantees"; a `.dll` therefore cannot be a contract at all, only a coincidence. [Rust-ABI] `abi_stable` is the honest escape hatch, but it targets "writing libraries loaded at program startup" and "a plugin system (without support for unloading)" — note that restriction: it cannot satisfy install/uninstall/upgrade at runtime. [abi_stable]

### (d) The plugin's *own persisted data*

- **What crosses:** a **declaration** (tables, columns, types, primary key, owner, retention, source projection) — not SQL. The host materializes it. This is exactly Fredo's existing model: `ApplicationDataTableDeclaration { name, primaryKey, columns[{name,type,nullable,owner}], source?, retention? }`, plus an `ApplicationDataDeclaration { applicationId, declarationRevision /* content hash */, tables }`. [fredo: declaration.ts]
- **Versioning unit:** `(contractMajor, declarationRevision)`. The revision is a **content hash of the declarations**, which gives idempotent materialization for free and detects out-of-band edits.
- **Compatibility rule:** additive-only within a MAJOR — new **nullable** (or defaulted) columns; no type change; no primary-key change; no rename. Anything else is a **new table + host-side backfill**, never an `ALTER`. Justification is protobuf's: reuse of a field number/slot "makes decoding wire-format messages ambiguous", and "the Protobuf wire format is lean and doesn't provide a way to detect fields encoded using one definition and decoded using another" — the SQL analogue is a reused column with stale rows. [Protobuf] §Consequences of Reusing Field Numbers
- **Raw DB access must be denied, not merely discouraged.** Three independent reasons: (1) it removes the host's only place to enforce row-level authority (complete mediation); (2) a plugin-issued `DROP`/`ALTER` destroys *other* plugins' rows in a shared cluster, violating least common mechanism; (3) it makes the host unable to promise "your data survives our upgrade", which is the entire value proposition of the declaration. Home Assistant's `domain` is likewise "never change" precisely because "config entries, entity IDs, and user automations all refer to it" — an identifier's durability is what makes declared state safe. [HomeAssistant-Manifest]
- **Deny-listing hook:** Tauri's model gives you the exact shape — `deny` scopes "always supersede the `allow` scope", so a host can post a global `deny` for the raw-SQL plugin and an `allow` for the declared-data command without ordering bugs. [Tauri-Scopes]

### Derived minimal manifest for a Fredo app package

Every field earns its place; the precedent column is why it is there rather than invented.

| Field | Type | Why it exists | Precedent |
|---|---|---|---|
| `$schema` | string (URI) | Makes the manifest self-describing and machine-validatable at install; JSON Schema says `$schema` "applies to the entire document and must be at the root level". | Grafana `$schema`; [JSONSchema-$schema] |
| `id` | string, reverse-DNS, immutable | Stable key for capabilities, tables, settings, and consent memory. Immutability is load-bearing, not cosmetic. | HA `domain` ("can never change"); Grafana `id` regex |
| `displayName` | string | UI label, may contain spaces — decoupled from the key. | VS Code `displayName` |
| `version` | SemVer 2.0.0 | Plugin's own evolution; drives upgrade/downgrade decisions. | SemVer; VS Code, Grafana, Obsidian |
| `engines.fredo` | semver range | Refuses install on an incompatible host *before* any code runs. | `contract` | `{ major, minor }` | The *contract* version (layers a–d) distinct from the plugin's own version — the OpenAPI separation of `openapi` (spec) from `info.version` (API). | [OpenAPI] §4.1 |
| `entry.logic` | `{ kind: "wasm"\|"sidecar"\|"none", path, abi }` | Declares *how* untrusted compute runs so the host knows which boundary to enforce. `"none"` is a first-class value (UI-only plugins). | Grafana `backend`/`executable`; Figma `main`/`ui` |
| `entry.ui` | string (relative path) | UI panel entry, sandboxed by CSP. | Figma `ui`; VS Code `browser` |
| `capabilities` | array of typed entries | **The authority grant.** Each entry names a capability and its scope; empty array means the plugin can do nothing (fail-safe default). | Figma `networkAccess`; Grafana `iam.permissions`; [Saltzer-Basic] |
| `capabilities[].net.http.allow` | array of URLPatterns | Egress allow-list, per-capability. `["none"]` must be expressible. | Figma `networkAccess.allowedDomains` |
| `capabilities[].rows.read/write` | array of `eventType`(+field filter) | Row-stream access at the *event-type* granularity, never the database. | Fredo layer (a); least-privilege |
| `data.tables` | array of declarations | The plugin's own persistent data, declared not executed. | Fredo `ApplicationDataTableDeclaration` |
| `data.tables[].retention` | `{ maxRows?, ttlDays? }` | Bounds storage growth at install time, not at 3am. | Fredo `retention`; HA `single_config_entry` spirit |
| `requires.apps` | array of app ids + ranges | Peer apps this app composes with. | Grafana `dependencies.plugins`; npm `peerDependencies` |
| `requires.capabilities` | array | Requests *another app's* exposed capability (host-mediated introduction). | Grafana `extensions.exposedComponents`; [Wikipedia-OCap] introduction |
| `integrity` | `{ algo, digest, signature, keyId }` | Provenance of the exact artifact bytes. | minisign key_id/signature; [minisign] |
| `maturity` | enum | Lets the host hide experimental plugins from consent prompts it cannot yet describe well. | Grafana `state`; HA `quality_scale` |
| `links` | `{ docs, repo, issueTracker }` | Support escape hatch; also what a consent dialog shows. | Grafana `info.links` (named `documentation`/`repository`/`raise issue`); HA `issue_tracker` |

Deliberately **absent**: a `main`-style unrestricted code path, a raw `sql` or `db` capability, any `permissions: ["*"]`, and any field that grants authority implicitly by being present (e.g. an `http: true` boolean) rather than explicitly with a scope.

## Threat model sketch

Assumed adversary: an installed third-party app package, and the publisher of that package. Assumed user: installs apps from a catalog, will click through a consent dialog.

| # | Scenario | What actually happens in each option | Mitigation | Citation |
|---|---|---|---|---|
| T1 | Plugin calls a first-party command it was never granted | **Today in Fredo:** succeeds. All `invoke_handler` commands are allowed to all windows, `app-*` is in the `default` capability, and there is no `permissions/` directory. | Adopt `AppManifest::commands(...)` to auto-generate per-command permissions; give plugin windows their **own** capability file; never include plugin labels in a `*` glob. | [Tauri-Capabilities]; [Tauri-Learn-Plugin-Perms]; fredo `build.rs`, `capabilities/default.json` |
| T2 | Plugin reads another application's declared rows | **Today in Fredo:** succeeds. `application_data_read` takes `applicationId` from the *argument*, and the window label is not consulted — the classic confused deputy. | Replace `applicationId: String` with a **host-minted capability handle** resolved from the caller's window label + granted scope; ignore any `applicationId` in the payload entirely. | [Wikipedia-ConfusedDeputy]; [Wikipedia-Capability]; fredo `application_data/commands.rs` |
| T3 | Plugin passes a name it does not own (path, table, event type) | Succeeds wherever the host resolves a name against ambient authority. Path traversal and table-name squatting are the same bug. | Fail-safe default + complete mediation: the host resolves every identifier from the token, never from the payload; reject unknown identifiers with a hard error. | [Saltzer-Basic] §I.A.3(b),(c) |
| T4 | Plugin logic crashes / loops / OOMs | In-process dylib: **host dies**. Sidecar: plugin dies, host survives (Grafana's stated reason for a subprocess backend: "A panic in a plugin doesn't panic the server"). WASI: component traps, host survives. | Never load third-party native code in-process. Prefer WASI; sidecar acceptable. | [Grafana-Backend]; [WASI-Security]; [abi_stable] |
| T5 | Plugin reads files it was not granted | In-process/dylib: succeeds (same user). Sidecar: succeeds unless the OS sandbox is added — **spawn scoping is not a filesystem sandbox**. WASI: fails at the import boundary. | WASI for untrusted; for sidecars, state explicitly that the OS user is the boundary and say so in the consent UI. | [Tauri-Sidecar]; [WASI-Security] |
| T6 | Plugin phones home to an undeclared host | Succeeds in every option unless egress is declared *and enforced at the network layer*. A manifest field alone is not a control. | Enforce the declared `net.http` allow-list in the host's HTTP proxy (Grafana's `routes[].url` pattern) rather than trusting the plugin. | [Figma-Manifest]; [Grafana-plugin.json] |
| T7 | Plugin ships a new version that exfiltrates via a *newly added* capability | The classic silent-escalation bug: upgrade re-uses prior consent. | Consent is bound to `(id, version, capability-set digest)`; any capability change re-prompts. This is separation of privilege applied to upgrades. | [Saltzer-Basic] §I.A.3(e) |
| T8 | Signature verified, then file swapped (TOCTOU) | Succeeds if the host hashes a path and then loads a path. CWE-367's canonical example is exactly `access()` then `fopen()` on a filename. | Open once, hash the open descriptor, and execute/instantiate **from that same descriptor** (or a copy made before verification). Re-verify on every load, including after update. | [CWE-367]; [minisign] |
| T9 | Publisher is compromised; attacker signs a *downgrade* to a previously-vulnerable version | Succeeds if only "signature valid" is checked. | Bind `id`, `version`, and `contract.major` into a **signed** metadata blob; reject a version lower than the installed one unless the user explicitly opts in. minisign calls this out: trusted comments "can be used to add… version numbers to prevent downgrade attacks". | [minisign]; [Sigstore] |
| T10 | Plugin declares a schema change that destroys user data | Succeeds if declarations are applied as `ALTER`. | Additive-only within a MAJOR; destructive change = new table + host backfill; keep protobuf's `reserved` analogue (retired columns stay retired). | [Protobuf]; fredo `declaration.rs` reserved columns |
| T11 | Plugin floods the row stream / subscribes to everything | Succeeds without quotas; degrades every other app (least common mechanism). | Per-plugin subscription and delivery quotas at the registry; the *host* enforces, not the plugin. | [Saltzer-Basic] §I.A.3(g) |
| T12 | Host is compromised via the webview (XSS in a plugin panel) | The plugin's webview inherits its capability set. CSP is "only enabled if set on the Tauri configuration file" and Tauri recommends the Isolation pattern to intercept **all** IPC because the threat is untrusted frontend content. | Keep a restrictive CSP (Fredo already disallows `unsafe-inline` in production `script-src`), put plugin panels behind the Isolation pattern, and remember capabilities are the *last* line, not the first. | [Tauri-CSP]; [Tauri-Isolation]; fredo `tauri.conf.json` `security.csp` |
| T13 | Plugin author abuses the *supply chain* of the host itself | Out of scope for any capability model — Tauri says so: capabilities do not protect against "supply chain attacks or otherwise compromised developer systems". | Pin, audit (`cargo audit`, `npm audit`), and sign releases; communicate the residual risk honestly. | [Tauri-Capabilities]; [Tauri-Lifecycle] |

**Residual risk that no mechanism here removes:** once you grant a plugin `rows.read` for an event type, you have granted *all* rows of that type, including any content a user later considers sensitive. Field-level filtering is the only real attenuation, and it must be a host-side projection (`select`), not a client-side filter — an attenuated reference, not a promise. [Wikipedia-OCap] attenuation

## Open questions (8)

1. **Does `add_capability` survive a window that already exists?** The docs show it in `setup`, before windows are built. Whether a capability added *after* a plugin window is created is consulted by the runtime authority on the next invoke is undocumented; this must be proven with a test before relying on install-time grants.
2. **`build.removeUnusedCommands` vs `dynamic-acl`.** The config reference warns it "won't be accounting for dynamically added ACLs when you use features from the `dynamic-acl` feature flag". If we ever enable command pruning in release builds, do runtime-granted permissions silently vanish? Needs a build-matrix experiment.
3. **Where does the plugin's webview actually live?** A same-origin `index.html?view=app&id=…` route shares the main webview's origin, so `default`'s `local: true` and any origin-based check cannot distinguish plugin UI from host UI. A separate origin (`tauri://plugin-<id>` / a custom protocol) or a separate `WebviewWindow` is required for origin-based scoping. Not resolved by the docs read.
4. **WASI maturity for this host.** WASI 0.3 is "Stable, current" and Wasmtime 46+ runs 0.3 by default, but "most other toolchains still target WASI 0.2". A Rust guest with 0.3 bindings is only `wasip3`-crate-level experimental. Which target do we commit a plugin SDK to?
5. **Component-model `resource` support in the chosen runtime.** Attenuated table handles are the right encoding for layer (d), but `own`/`borrow` handle support varies by host runtime. Needs a spike.
6. **Consent semantics for `requires.capabilities`.** Grafana models cross-plugin composition as `extensions.exposedComponents` and Backstage as `relations`; neither documents a *permission* prompt for "app A may call app B's capability". Whether the host or the user grants that is a product decision, not a technical one.
7. **Migration tooling for declared tables.** `sqlx::migrate!` is embed-time and static; a plugin's declarations are dynamic. Either we generate migrations from `declarationRevision` diffs (and must reconcile the LF/CRLF hash caveat), or we forbid `ALTER` entirely and rely on new-table+backfill. Recommendation is the latter, but the backfill ownership (host vs plugin) is unsettled.
8. **Signature root of trust.** minisign (self-managed Ed25519 key) vs Sigstore keyless (Fulcio/Rekor, TUF root). Keyless gives transparency and no long-lived key, but requires network access to Rekor at verify time and a TUF root in the app — an offline-first desktop app may not be able to verify without a cached bundle. Unresolved.
