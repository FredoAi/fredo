# Pipeline hygiene exploratory tests

Unscripted probes — add findings on the fly; confirmed findings promote to `functional.md` as `F-<n>` rows (keep the origin note). **This is a config-only / static-policy slice (G-089) — no product runtime, no `telemetry_spans`.** The probes below target GitHub's comment-authorization + lock behavior, the repo interaction-limit semantics, and the pipeline state machine's comment read/write path. Each probe is verified against the GitHub REST API / `gh` CLI / the offline harness, not the Fredo app.

- [ ] E-1 Probe: **re-application cadence of the temporary interaction limit.** The repo interaction limit has `expiry` max `6_months` (NFR-WINDOW-1). What is the observed/configured expiry? Does anything remind or re-apply it before it lapses? Simulate/probe the state after expiry — does the repo silently return to comment-open, and is that documented? (The durable guard should be the per-conversation lock-on-create, not this temporal control.)
- [ ] E-2 Probe: **lock-reason metadata semantics.** `active_lock_reason: "off_topic"` is informational only — it does not gate commentability (the lock itself does). Confirm by: reading the lock reason, then confirming that a maintainer/machine comment still lands (proves reason does not restrict the write-capable). Does the reason survive issue state changes (reopen/close)? Is the four-value enum (`off_topic`/`too heated`/`resolved`/`spam`) respected, and is a value outside the enum rejected?
- [ ] E-3 Probe: **REST vs GraphQL lock-state consistency.** Read lock state via `gh api repos/.../issues/<n>` (`locked`, `active_lock_reason`) AND via GraphQL `locked { lockedReason }`. Are they consistent (both `true` / `off_topic`)? Note any field-name/casing drift the verifier must account for.
- [ ] E-4 Probe: **non-pipeline bot/dependabot comments.** A bot that is NOT the state machine's own principal (e.g. dependabot, or any GitHub App) — is its comment flagged as external? Confirm the allowlist is role-based and does not blanket-trust every `BOT`/`MANNEQUIN`, but only the pipeline's own posting principal.
- [ ] E-5 Probe: **belt-and-suspenders gap.** If an issue is NOT locked (e.g. a `temp:` harness issue, or a pre-hardening open issue that slipped the lock pass) but the repo interaction limit is `collaborators_only`, is a non-collaborator comment actually blocked by the limit alone? Does the limit alone close the AC2 boundary for an unlocked issue, or is the per-issue lock necessary?
- [ ] E-6 Probe: **repo-wide interaction-limit blast radius.** `collaborators_only` is repo-wide — probe a NON-pipeline issue: can a collaborator still comment? Can a non-collaborator still OPEN a new issue (interaction limits restrict commenting/creating based on the limit value)? Record whether the limit over-restricts legitimate public contribution (e.g. a genuinely external bug report on a non-pipeline issue).
- [ ] E-7 Probe: **lock-on-create timing.** Does the newly created backlog issue become `locked:true` in the SAME `create-issue` action (no manual follow-up, config completeness — NFR/AC4), or is there a window between creation and lock where a comment could land? Probe the create flow with the offline mock (`FREDO_MOCK_GH=1`) and, if permitted, a scratch issue.
- [ ] E-8 Probe: **mock fidelity (harness vs real GitHub).** The offline mock must model `gh api` lock/interaction-limit and comment `authorAssociation` so `test-scripts.ps1` stays green. Probe that a `gh api` lock/interaction-limit call driven through `FREDO_MOCK_GH=1` behaves the same as the real one (same args, same response shape) — a divergence is a harness fidelity gap.
- [ ] E-9 Probe: **pre-lock vs post-lock external comment timestamps.** For flagged (external) comments, does the trusted-author filter key off `authorAssociation` alone, or also off a timestamp relative to the lock? Confirm that no pre-lock external comment can silently become trusted context (AC5 "never silently feeds agent context") merely because it predates the lock.
- [ ] E-10 Probe: **the state machine does not lose write access on a locked issue.** The machine's token runs as the write-access principal (the `pktron`/maintainer principal in `.github/CODEOWNERS:1`). Probe that a locked pipeline issue remains fully write-capable for the machine across a real post-lock comment, a verdict flush, and the `testing → audit` merge — no 403 and no token re-auth needed (NFR-CAPABILITY-1).
- [ ] E-11 Probe: **`author_association` for the feature issue's own timeline.** For #2797 itself (rather than a scratch issue), list comments and inspect `author_association` values — does the set include a non-write role that the pipeline must exclude, and does the round-aware verification guard's `latest_evidence_comment` correctly skip it?
