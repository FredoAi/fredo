# Pipeline hygiene functional tests

Derived from the #2797 QA Plan. **Verification policy: `static`** — this is a **GitHub-repo-config / pipeline-hardening slice with NO product runtime and NO `telemetry_spans`** (justification in the QA Expert A2A section). The verifier drives the **GitHub REST API / `gh` CLI against `FredoAi/fredo`** and the pipeline state machine — **not** the Fredo app. Where a live product/telemetry leg would normally appear for a `live`-policy spec, note that **no `telemetry_spans` leg applies** here.

**Verifier note on the harness:** `gh api` returns REST raw JSON (snake_case, e.g. `author_association`, `active_lock_reason`); `gh issue view --json <field>` returns `gh`-normalized camelCase (e.g. `authorAssociation`, `activeLockReason`). GraphQL returns camelCase (`lockedReason`). Both spellings are used below where each is the real payload.

**Open pipeline-issue set definition (the "pipeline issue" set, used by F-1/F-2/F-3/F-5):** every issue the state machine tracks via a pipeline label — `backlog`, `planning`, `ready-for-dev`, `testing`, `audit`, `cleanup`, `done` (and the `bug` label) — OR an open issue carrying a `spec/<n>` branch, OR the feature issue itself (#2797). Minimum required open set: **#2795, #2773, #2797**. Closed/done issues are out of scope (require no lock).

---

- [ ] F-1 (AC1) Enumerate open pipeline issues and confirm each is conversation-locked. Expected: `gh issue list --state open --json number,labels,title` returns the pipeline issue set; for EACH open pipeline issue `gh api repos/FredoAi/fredo/issues/<n>` reports `locked: true`; zero open pipeline issues are unlocked. The lock reason matches the triage-chosen value `off_topic` (`active_lock_reason` / GraphQL `locked.lockedReason`). Edge: a pipeline issue that closes mid-run is excluded as `not open` (not a failure); closed/done issues are never part of the set; #2795/#2773/#2797 must all be present and locked. **No `telemetry_spans` leg — config-only.**
- [ ] F-2 (AC2) A non-collaborator comment on a locked pipeline issue is blocked with an observable lock reason. Expected: `gh api repos/FredoAi/fredo/issues/<n>/comments` (or `gh issue comment <n>`) as a token/account with **no write access** returns HTTP 403 / "This conversation is locked" and the comment is NOT created; and the lock state read (`GET .../issues/<n>`) reports `active_lock_reason: "off_topic"`. Edge: if no external token is available, verify the boundary by the documented fallback — assert `locked: true` + persisted `active_lock_reason: "off_topic"` (GitHub enforces the block at its auth layer) and record that as the fallback in the evidence; distinguish a **lock-block** from a **repo-permission-block** (lock-block is a 403 on the comment endpoint of a `locked:true` issue regardless of repo read permission); the lock reason is informational metadata only — it does not change who may comment (the lock itself does). **No `telemetry_spans` leg — config-only.**
- [ ] F-3 (AC3) Maintainers/collaborators AND the state machine can still post `Status`/`Triage Plan`/`Tests Runs` comments on a locked issue. Expected: a collaborating agent/tester posts via the state machine (`comment --prefix Status` / a pending draft flush: `triage-plan.md` → `## Triage Plan`, `tests-runs.md` → `## Tests Runs`) onto a locked issue → HTTP 201 and the comment appears on the timeline; no 403 lock error; subsequent pipeline phases proceed. Edge: exercise each relevant prefix on the locked issue; confirm the lock does NOT break the state machine's auto side-effects (project Status-field transition mirror, `tests-commit`, plan assembly); prefer posting on a benign/scratch pipeline issue rather than the live feature issue. **No `telemetry_spans` leg — config-only.**
- [ ] F-4 (AC4) A repo-level guard is active for future issues AND a newly created backlog issue is comment-safe at birth. Expected: (a) `gh api repos/FredoAi/fredo/interaction-limits` reports `limit: "collaborators_only"` (a valid GitHub enum; NOT `contributors_only`/`existing_users`) at repo scope, AND/OR a documented lock-on-create policy exists (search `CONTRIBUTING.md`, `docs/`, `.github/`); (b) `gh issue create` (via the state machine `create-issue`) yields a newly created backlog issue that is born `locked:true` (or protected by the interaction limit so non-collaborator comments are stopped). Pass if ≥1 repo-level guard IS present AND the new issue is comment-safe; fail only if there is NO guard, NO documented policy, AND a new issue is born unlocked. Edge: the interaction-limit window must match the planning decision (`6_months` default; temporary by design — the re-apply cadence must be documented, NFR-WINDOW-1); verify the lock-on-create mechanism actually yields `locked:true` at creation, not via a manual follow-up (config completeness); interaction limits are repo-wide and affect all issues — record whether it breaks collaborator commenting on non-pipeline issues. **No `telemetry_spans` leg — config-only.**
- [ ] F-5 (AC5, negative) Every pre-existing external-author comment on open pipeline issues is flagged and excluded from every context/verdict read. Expected: for each open pipeline issue, `gh api repos/FredoAi/fredo/issues/<n>/comments` and read each comment's `author_association`; every comment whose value is NOT a write-capable role is flagged/identified (manifest recorded) so it is excluded from agent context; the flagged count matches the observed external-comment count. **Trusted (write-capable) roles = `OWNER`/`MEMBER`/`COLLABORATOR` PLUS the pipeline's own posting principal (`BOT`/`MANNEQUIN` — the state machine posts `Status`/`Triage Plan`/`Tests Runs` as a bot/mannequin, so those MUST NOT be flagged or verdict parsing breaks). Flagged roles = `NONE`/`CONTRIBUTOR`/`FIRST_TIME_CONTRIBUTOR`/`FIRST_TIMER`.** Edge: bots/dependabot that are NOT the pipeline's own principal are external; PR comments vs issue comments; timestamps relative to the lock; the pipeline's trusted-context ingestion (`get_issue_comments`/`latest_evidence_comment`/`count_verdict_comments_in_round`) MUST ACTIVELY exclude flagged authors, not merely note them — otherwise AC5 is a silent false pass. **No `telemetry_spans` leg — config-only.**
