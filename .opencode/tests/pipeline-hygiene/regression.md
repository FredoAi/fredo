# Pipeline hygiene regression tests

Baseline invariants ("must not change") from the #2797 plan's non-goals / NFRs. **This spec is config-only (G-089) — no product runtime — so the no-regression baseline is about the pipeline harness, GitHub write path, GitHub repo state, and the product source tree, NOT about `telemetry_spans` or a `cargo`/`pnpm` build.** Every case is verified against the offline harness, the GitHub REST API, and a static `git diff` — no product/telemetry leg applies.

- [ ] R-1 State machine writes still post on a locked issue: after the hardening pass, `comment --prefix Status`, a `Triage Plan` draft flush, and a `Tests Runs` draft flush each still succeed (HTTP 201) on a locked pipeline issue; no 403 lock regression. This preserves AC3 and the round-aware verification guard. **No `telemetry_spans` leg — config-only.**
- [ ] R-2 The state machine's auto side-effects are unbroken post-lock: the `triage → implementation` transition still mirrors the phase onto the GitHub project Status field, persists the QA-seeded suites via `tests-commit`, and assembles the `## Triage Plan` draft; the `testing → audit` merge still opens/merges the spec PR. A lock must not stall these.
- [ ] R-3 Product source tree unmodified (NFR-NOPRODUCT-1): the spec branch diff against `main` for this spec contains ONLY `.opencode/scripts/pipeline-state.rs`, `.github/`, `docs/agentic-pipeline/`, `docs/SECURITY.md`, and `CONTRIBUTING.md` — it MUST NOT touch `apps/tauri/src-tauri/**`, `apps/ui/src/**`, or `apps/opencode-plugin/**`. Verify via `git diff --name-only main...HEAD` (or the `testing → audit` merge diff).
- [ ] R-4 Verification stays `static` (G-089): no native build gate is prescribed or required — the spec must NOT gate a PASS on `cargo check` under `apps/tauri` or `pnpm build`; the required local receipt is `powershell -File .opencode/scripts/test-scripts.ps1`. If a tester's evidence depends on a build to pass, that is a regression (false gate).
- [ ] R-5 Offline harness stays green (NFR-HARNESS-1): `powershell -File .opencode/scripts/test-scripts.ps1` passes after any `.opencode/scripts/` edit — the mock must model `gh api` lock/interaction-limit and comment `authorAssociation`; all harness tests report total/passed/failed with zero failures. A mock that bails on the new `gh api` paths is a regression.
- [ ] R-6 Trusted-author filter must NOT exclude the pipeline's own comments (AC5/REQ-05): `get_issue_comments`/`latest_evidence_comment`/`count_verdict_comments_in_round` must continue to parse `Status`, `Triage Plan`, and `Tests Runs` verdict comments posted by the machine's own principal (`BOT`/`MANNEQUIN`, or the `OWNER`/`MEMBER`/`COLLABORATOR` write role it runs under). Excluding the machine's own comments breaks the exit gate and is the exact regressions the allowlist is designed to avoid.
- [ ] R-7 Existing issue bodies are untouched: the hardening does NOT edit/redact/delete any existing issue body or comment body (a stated non-goal); only the lock state, interaction limit, and the trusted-author filter are added. Verify a spot pre/post comment body is byte-identical.
- [ ] R-8 No issue is closed/canceled/unlabeled by the hardening: ST-1's non-goals are that lock-on-open does NOT close, cancel, or re-label any tracked issue; lock state is set independently of issue state.
- [ ] R-9 `temp:` harness issues are not locked: `test-scripts.ps1` creates/consumes `temp:` issues that must remain unlocked for comment and close during a test run (ST-1/ST-2 non-goal). Locking a `temp:` issue during a harness run is a regression.
- [ ] R-10 The repo interaction limit does not break collaborator commenting: with `collaborators_only` active, a collaborator can still comment on any issue (pipeline or non-pipeline) — verify a maintainer comment lands on a non-pipeline issue (repo-wide scope must not over-restrict write-capable users).
- [ ] R-11 Documentation reflects that the interaction limit is temporary (NFR-WINDOW-1): `docs/agentic-pipeline/github.md` and the policy docs state the re-apply cadence (`6_months` default) so the temporal control is not mistaken for a permanent one; the durable guard is documented as per-conversation lock-on-create.
- [ ] R-12 The lock reason value is `off-topic` and is described as informational metadata only (NFR-LOCKREASON-1): the docs/repo state use one of GitHub's four enum values and never imply the reason gates commentability (the lock does).
- [ ] R-13 Overlapping suite: `.opencode/tests/oss-launch/` — the repo-now-PUBLIC surface and any interaction-limit/issue-policy behavior must not break the oss-launch functional/regression baselines (public-repo launch + contribution flow). Re-run when the pipeline-hygiene surface changes.
