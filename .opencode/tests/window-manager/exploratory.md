# Window Manager — Exploratory Probes (Spec #2807 — Own window-system kernel)

> Unscripted edge/failure probes for the own window-engine surface. A CONFIRMED finding promotes to `functional.md` as a new `F-` case (keep the origin note). Drive via `pnpm dev:tauri`; confirm the selected window via DOM before each capture (G-035); read the webview console after every probe.

## Probes to run beyond the script

- [ ] E-1 (OPEN — rapid double-open): Rapidly trigger two (or three) opens of the same feature id — does the engine ever stack a duplicate window/frame, or does it stay at exactly one window? Confirm via DOM + screenshot. (Promotes to functional F-9 if it duplicates.)
- [ ] E-2 (OPEN — update-while-minimized): Open a feature window, drive an update (state change), then minimize it, then drive ANOTHER update — does the update silently restore the minimized window or steal focus, or does the window stay minimized (and minimized in the a11y tree) until an explicit focus/restore? Cross-check DOM + a11y snapshot.
- [ ] E-3 (OPEN — close-from-any-z-order): With three windows stacked, close the BACKGROUNDED (unfocused) window, then close the FOCUSED (topmost) window — does each close succeed, and does focus move to the correct next topmost visible window (or the workspace) after each? Does a close from any z-order position leave a clean stack?
- [ ] E-4 (OPEN — backdrop/drag-area boundaries): Drag a window by its header toward the top of the workspace — is the title bar clamped so it stays within the workspace top, or can it be dragged off-screen/into the toolbar? Pointerdown on a 28px control cluster or on a resize grip — does it correctly NOT start a drag (stop propagation)? Does a drag ever leave the window unreachable?
- [ ] E-5 (OPEN — resize grip boundaries/geometry): Resize a window via each of the 8 grips — does only the correct edge/corner resize, and is a min width/height enforced (can it be crushed to zero)? Double-click the header while maximized/restored — does it toggle correctly, and does a maximized window allow drag/resize at all (it should not)?
- [ ] E-6 (OPEN — persisted legacy windowStyle values): Pre-seed each legacy value in turn (`default`, `traffic`, `linux`, `yk2000`, `aero`) plus a bogus/unknown value and a null/absent key, reloading the app for each — does every case render the SINGLE brand chrome with no divergence and no throw? Confirm console + system logs are clean each run. (A divergence or throw is a defect; a confirmed mismatch for any value promotes to functional F-15.)
- [ ] E-7 (OPEN — maximize→restore geometry): Maximize a window that had been dragged/resized, then restore — does it return to the PRIOR float geometry (size + position), not a default/reset geometry? Does maximize while already maximized toggle to restore?
- [ ] E-8 (OPEN — keyboard shortcuts + focus management): Open a window and drive `CmdOrCtrl+W` (close), `CmdOrCtrl+M` (minimize), `CmdOrCtrl+Shift+M` (maximize/restore), `Ctrl+Tab`/`Shift+Ctrl+Tab` (focus next/prev). Does focus land on the expected window/control, does the minimized window leave the tab order, does `:focus-visible` outline use the accent token? Any shortcut conflict or focus trap is a defect.
- [ ] E-9 (OPEN — high window-count): Open many feature windows in sequence — does z-order/focus remain correct, does the stack stay manageable (no window unintentionally lost behind the toolbar or off-screen), does the open-window list (toolbar multi-window suffix) stay accurate?
- [ ] E-10 (OPEN — a11y semantics): Snapshot the accessibility tree of a window — is the frame a non-modal group named by the window title (NOT a modal `role="dialog"`), are min/max/close exposed as labeled tabbable buttons, and is a maximized window's control announced via `aria-expanded`? Is a minimized window hidden from the a11y tree?
- [ ] E-11 (OPEN — prefers-reduced-motion): With `prefers-reduced-motion` reduced, do the focus/z-order/halo transitions respect it (subtle opacity/inset only, no distracting motion)? Any jarring animation is a defect.
- [ ] E-12 (OPEN — theme/accent override re-tint): Override the user accent and toggle light/dark — does the whole chrome re-tint from the theme tokens (frame border, halo, icon tile, brand cap, control hover), including the focused vs unfocused frame distinction? A fixed non-token color that ignores the accent is a defect (N-1/R-6).
