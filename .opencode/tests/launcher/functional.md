## F-3 — Tile select opens the feature through the own kernel (AC2b)
- [ ] F-3: Focus the grid, arrow to a tile, press Enter. **Expected:** the feature window opens (WindowFrame + feature title + content appears in the DOM snapshot); it is focused; `useWindows()` gains the entry. The open routes through `onOpenFeature(id, feature)` → own-kernel `openWindow`.
  - **FAIL.** Keyboard Arrow→ / ArrowLeft then Enter on a tile DOES route: the launcher closes and a `div.fredo-window__surface` appears in the DOM (`header.fredo-window__header` + content), and the open goes through `onOpenFeature(id, feature)` → Home `openFeatureWindow` → own-kernel `openWindow` (verified: Query Viewer and Mission Monitor both opened in DOM). **BUT the opened feature window renders BEHIND the desktop background — it is NOT visually observable.** Diagnostic: `document.elementFromPoint(960,500)` returns the desktop `#lights` canvas, not the window; both `launcher-open` screenshots (turbo + classic; Query Viewer + Mission Monitor) show the desktop with NO window despite the DOM surface existing; only after manually raising the window-container z-index to `100` does the window paint (see `aqu2b-missionmonitor-zfix.jpeg` — Mission Monitor's full Session-Stack UI). Root cause: the window-manager container is `position:absolute; z-index:auto` (`WindowManager.tsx:25`) while `DesktopBackground` is `position:absolute; z-index:0` (`DesktopBackground.tsx:38-44`) and is rendered later in DOM order, so the desktop paints on top. This is a z-order occlusion defect and is NOT introduced by the launcher spec's ST-1 diff (which only swapped `DesktopToolbar`→`LauncherShell`; the WindowManager/DesktopBackground order is unchanged). **Expected-vs-actual:** user selects a tile → launcher collapses but NO feature window appears on screen. **Repro:** open launcher → Arrow→ to tile → Enter; the launcher closes and no window is visible; check `elementFromPoint(windowCenter)` returns the desktop canvas.
- [ ] F-3 edge: Opening an already-open tile re-focuses (no duplicate) per `windowStore.ts:68-91`; multi-window features get a suffixed id.
  - **UNVERIFIED (named blocker).** The window-occlusion defect (see F-3) prevents reliable visual observation of re-focus / multi-window id behavior (the opened windows cannot be seen to confirm focus/id). The direct `useWindows()-gains-entry` and single-open path was verified in DOM (Query Viewer + Mission Monitor each opened once); the re-focus and multi-window legs were not observed because the occluded window cannot be visually inspected.
