# app-dock — Functional

Scope: the positionable open-apps dock surface — **Sidebar** (left-edge vertical rail) vs **Bottom bar** (bottom-center horizontal pill), selectable under Settings → Appearance — extending the #2838/#2841 left-edge dock (resting-visible on a clean desktop, edge-peek overlay reveal when a window covers the desktop, hover/focus ✕ close). Seeded from issue #2848; map 1:1 to `.opencode/tmp/2848/triage.md` `## QA Expert` (QA Plan F-1..F-12, F-6a/F-6b split).

> **Verification policy: live** — pure-rendering UI spec (position choice, edge-summon reveal/hide, hover ✕, persistence); ACs provable ONLY by observing the running artifact (`pnpm dev:tauri` serving `spec/2848`, MCP driver `com.fredo.app:9223`). DOM snapshots, `getBoundingClientRect`/computed-style probes, real `webview_interact` pointer/keyboard drives, and `tauri_webview_screenshot` receipts per orientation. NO telemetry surface — the live-gate reference is the established desktop-shell F-14 / desktop-chrome F-23 pattern: `SELECT COUNT(*) FROM telemetry_spans` non-zero + recent `max(ingested_at)` at round start (the dock is row-INDEPENDENT — entries come from the `useWindows()` store, opened via the launcher grid). A static-only PASS is a FALSE PASS. A console `Error:`/`Uncaught`/`Maximum update depth exceeded` on any leg invalidates that leg's evidence.

- [ ] F-1 (AC1 — setting surface): Open Settings (chrome `[aria-label="Settings"]`, clean desktop) → Appearance section; locate the **Dock position** control. **Expected:** a **Dock position** field renders in the Appearance section (the auto-discovered appearance content — `ThemingSettings`/the Architect's chosen surface in ProfileSettingsModal) offering exactly **Sidebar** and **Bottom bar** options; the default reads **Sidebar** on an existing install; label/options match the backlog wording.
  - **Edge:** the Settings modal must be CLOSED before any dock geometry/reveal probe (an open Chakra dialog z:1500 masks dock hits — #2841 F-18 precedent); the field is a `chakra.select` styled via theme CSS vars, NOT a `NativeSelect` (unstyled browser default = FAIL); the control lives in ProfileSettingsModal, never the legacy tabbed `SettingsPanel`.
- [ ] F-2 (AC1 — immediate move, both directions): With ≥1 window open (mix minimized + floating) on a clean desktop, select **Sidebar** → observe; select **Bottom bar** → observe; select back. **Expected:** the dock relocates IMMEDIATELY on selection WITHOUT an app restart: Sidebar = left-edge vertical rail (resting-visible, x≈0); Bottom bar = bottom-center horizontal dock (`position:fixed`, bottom-anchored, horizontally centered); the SAME open-app entries render in both; NO leftover dock element at the previously-chosen edge (exactly ONE dock in the DOM).
  - **Edge:** rapid toggle Sidebar→Bottom bar→Sidebar (no stale/duplicate dock, no `Maximum update depth exceeded`); selection while 0 windows open (dock absent — the setting still persists); narrow viewport (bottom bar not clipped/off-screen).
- [ ] F-3 (AC1 — persistence): Select **Bottom bar**; FULLY restart the app (kill + relaunch `pnpm dev:tauri`); reopen with ≥1 window on a clean desktop. **Expected:** the dock renders at the LAST-chosen edge (bottom bar) after the full restart — the default (Sidebar) must NOT re-assert. Setting persisted via the app settings store (FeatureStore/AppStore → `Fredo_dock_position`), NOT a `useRef`/component flag.
  - **Edge:** persistence for **Sidebar** when chosen explicitly; unknown/corrupt persisted value (bogus enum) degrades to **Sidebar** without crashing (graceful default, console clean); the persisted key is readable in the store (FeatureStore/AppStore query) after restart.
- [ ] F-4 (AC2 — resting-visible, both orientations): All windows minimized / none showing → clean desktop (`coveredByWindow === false`); with the pointer AT REST (no edge gesture), snapshot + `getBoundingClientRect` the dock per orientation. **Expected:** Sidebar — dock `visibility:visible`, `pointer-events:auto`, resting transform `translate(0px,-50%)` at the left edge (x≈0, NOT off-canvas `-100%`), entry list visible. Bottom bar — dock visible, bottom-anchored + horizontally centered, NOT off-canvas (no `translateY` hide). Stays visible until covered or the position changes.
  - **Edge:** 0 windows → NO dock at either edge (empty gate holds in both orientations — `dockPresent:false`, no listener, no ghost); all-minimized vs all-closed transitions; light + dark presets; narrow viewport (bottom bar fits, not clipped).
- [ ] F-5 (AC2 — entry parity + empty gate, both orientations): Compare dock entries to the `useWindows()` store set per orientation; close the last window. **Expected:** the dock lists every open window exactly once in store order (same icons/entries in BOTH orientations — entries carry the SAME `aria-label` app title + state); closing the last window removes the dock entirely (no empty rail/pill, no ghost element).
  - **Edge:** minimized + floating mix; same-feature double-open (one entry per feature id); entry set == store set after every settle (no stale/ghost entries in either orientation).
- [ ] F-6a (AC3 — reveal, Sidebar): Maximize a window (covers the left edge, full-bleed). With the dock at rest (hidden, off-canvas), move the pointer to the far LEFT edge (`clientX ≤ 6` reveal zone, mid-height) — real pointer + document-`pointermove` dispatch. **Expected:** the dock slides IN as an OVERLAY on top of the maximized window (`zIndex:1200`, above the window stack): computed `visibility:visible`, `pointer-events:auto`, x≈0 (not off-canvas), showing its open-app entries over the window content. The window stays full-bleed (NO content re-indent).
  - **Edge:** `clientX=6` boundary (≤6 reveals, >6 does not); reveal fires on edge ENTRY (no dwell requirement); pointer resting INSIDE the dock keeps it open (no flicker/stuck); 5+ reveal/hide cycles clean (no `Maximum update depth exceeded`); reveal NOT triggered by click/focus alone (pointer-only).
- [ ] F-6b (AC3 — interaction over the overlay): With the dock revealed over a maximized window, click an app entry; then re-reveal and click its ✕. **Expected:** clicking a docked app's entry focuses/restores that window (topmost, accent treatment) — a docked app is activatable while the dock floats over the maximized window. Clicking `.dock-close` (`aria-label "Close <title>"`) closes ONLY that app (its entry drops); other entries remain; the ✕ reveals on row hover / `:focus-within` (`opacity 0→1`, `pointer-events none→auto`).
  - **Edge:** close of focused vs minimized vs backgrounded app from the revealed dock; the ✕ click never double-fires the row's activate (`stopPropagation`); the dock stays revealed/usable over the maximized window during interaction.
- [ ] F-7 (AC3 — hide): With the dock revealed over a maximized window, move the pointer AWAY past the keep-zone (`DOCK_WIDTH_PX + DOCK_KEEP_MARGIN_PX`, i.e. > ~76px) and hold outside past the hide-delay grace (~350ms). **Expected:** the dock slides away (`visibility:hidden` after the slide, off-canvas, `pointer-events:none`), leaving the maximized window FULLY unobstructed and full-bleed (no indent — `elementFromPoint` at the edge returns the window, not the dock).
  - **Edge:** pointer returns inside the keep-zone before the grace expires → dock stays (hide cancelled); pointer inside the dock suspends auto-hide; keyboard focus inside the dock suspends auto-hide (no dock hides under an active keyboard user); ESC hides + restores focus (edge-peek branch only); hide-delay timing ≈350ms (slide completes, THEN visibility flips).
- [ ] F-8 (AC4 — ✕ reveal + close, both orientations): Hover an open-app icon (each orientation) → ✕ appears top-right of the icon well; activate it → closes that app; hover away → ✕ hides (`opacity 0`). **Expected:** in BOTH orientations `.dock-close` reveals on row `:hover` / `:focus-within` (`opacity:1`, `pointer-events:auto`), its hidden state is opacity-hidden NOT `display:none` (stays in the tab order), `aria-label="Close <title>"`, and clicking it closes ONLY that app. The ✕ NEVER renders for a window whose `win.canClose` is false (no close button in the entry).
  - **Edge:** minimized/background/focused app ✕; a keyboard-revealed ✕ (`focus-within`) activates without launching/activating the app; hover-away before activation closes nothing.
- [ ] F-9 (AC4 — keyboard ✕): Tab/focus an app entry (roving keys) so `:focus-within` reveals the ✕; activate it with Enter (keyboard tool). **Expected:** the ✕ becomes visible on entry focus; Enter on the focused ✕ CLOSES that app WITHOUT activating/focusing/restoring it (the entry's activate is NOT fired); `stopPropagation` keeps the row dispatch silent. The app's window closes and its entry drops.
  - **Edge:** Enter on the ✕ vs Enter on the entry icon are distinct outcomes (activate = focus/restore vs ✕ = close); the ✕ of a `canClose:false` window is absent from the tab order too; the `:focus-visible` ring on the ✕ uses the accent token (`tint('var(--accent-primary)',40)`).
- [ ] F-10 (AC5 — switch while maximized): With a window MAXIMIZED (dock hidden, edge-peek model active), open Settings → Appearance and change Dock position Sidebar ↔ Bottom bar; then probe the newly-chosen edge. **Expected:** changing position while a maximized window covers the desktop applies reveal behavior at the NEWLY chosen edge — the maximized window stays unobstructed (full-bleed at the OLD edge, no leftover dock there) and edge-summon (reveal zone + slide-in + hide) works at the NEW edge. The choice persists (F-3 leg after this switch).
  - **Edge:** switch maximized→restore→maximize cycles (reveal follows the current edge, no stale-edge dock); rapid position flips under a maximized window; no `Maximum update depth exceeded` from the orientation flip (transition-only reveal preserved); the old edge is NOT a second reveal surface (only the chosen edge summons). Sequencing: the Settings button sinks to z0 under a maximized window — open Settings BEFORE maximizing, or restore→open→re-maximize (#2841).
- [ ] F-11 (AC5 — keyboard roving, both orientations): Reveal the dock; keyboard-drive with per-orientation roving keys. **Expected:** Sidebar — ArrowUp/ArrowDown rove between entries (Home/End = first/last; #2838 F-35 roving precedent). Bottom bar — ArrowLeft/ArrowRight rove between entries (left/right horizontal layout). Enter/Space activates the focused entry; Tab reaches each entry's ✕ in BOTH orientations; the ✕ is keyboard-reachable in both; ESC hides (edge-peek) + restores focus.
  - **Edge:** direction semantics MUST match the orientation (Sidebar up/down only, Bottom bar left/right only — cross-axis keys are a FAIL); keyboard focus inside the dock suspends auto-hide (no dock disappears mid-keystroke); a hidden (covered) dock is out of the tab order + a11y tree (no invisible-focus trap when the dock hides).
- [ ] F-12 (NFR — tooltip placement per orientation): Hover an entry icon in each orientation; snapshot the Chakra tooltip. **Expected:** the tooltip appears on hover AND keyboard-focus; Sidebar (left rail) — tooltip opens to the RIGHT of the well (`placement:"right"` baseline), never clipped at the left viewport edge; Bottom bar — tooltip opens ABOVE the well, never clipped at the bottom viewport edge. Content = app/window title; closes on leave/focus-out (`closeDelay={0}`, no sticky tooltip).
  - **Edge:** long app titles; narrow viewport (no clip per orientation); tooltip readable in light + dark; no double-announce via `aria-describedby` when the tooltip rides the real-button accessible name (DockEntry has real-button labels — the tooltip is never the SOLE label).
